Interface copy is the short text people act on, such as a button label or an
error message. Each kind follows the same pattern on every screen, so the
reader learns it once. Write it with [Voice and tone](/content/voice-and-tone)
and [Language and grammar](/content/language-and-grammar), which this page
doesn't repeat.

## Buttons

### Name the action

A label is a verb that says what happens when the reader presses it. Add the
thing it acts on when the verb alone could mean more than one thing. Keep it
to two to four words.

<PairTable>

| Write           | Not     |
| --------------- | ------- |
| Save changes    | Submit  |
| Add ticket type | New     |
| Publish event   | OK      |
| Delete event    | Yes     |
| Buy tickets     | Proceed |

</PairTable>

<Guidelines>

<Guideline
  headingLevel={3}
  title="Say what it costs"
  description="A button that takes money or can't be undone says so on the label."
>
  <Guideline.Do example={<Button intent='accent' emphasis='strong'>Pay $96</Button>}>
    Put the amount on the button that takes the payment.
  </Guideline.Do>
  <Guideline.Dont example={<Button intent='accent' emphasis='strong'>Continue</Button>}>
    Don't hide a payment behind a word that sounds like the next step.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="Links name the destination"
  description="A link, or a button with an href, says where it goes, so it makes sense read on its own."
>
  <Guideline.Do example={<Button href='#'>View orders</Button>}>
    Name the page the reader lands on.
  </Guideline.Do>
  <Guideline.Dont example={<Button href='#'>Read more</Button>}>
    Don't make the reader read around the link to learn where it goes.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="Label every icon button"
  description="An icon button has no visible words, so its aria-label carries them. Name the action, not the picture."
>
  <Guideline.Do code={`<IconButton aria-label='Remove ticket'>`}>
    A screen reader says what the button does.
  </Guideline.Do>
  <Guideline.Dont code={`<IconButton aria-label='Bin'>`}>
    Don't describe the icon. The reader hears what it looks like, not what it
    does.
  </Guideline.Dont>
</Guideline>

</Guidelines>

## Form help

### Labels

A label is a short noun phrase, with no colon and no instruction.
`showIndicator` on `Field.Label` marks required and optional fields, so a
label never carries an asterisk.

<PairTable>

| Write            | Not                       |
| ---------------- | ------------------------- |
| Email            | Enter your email address: |
| Mobile number    | Phone #                   |
| Ticket type name | Name \*                   |
| Date of birth    | DOB                       |

</PairTable>

<Guidelines>

<Guideline
  headingLevel={3}
  title="Helper text says what the reader can't guess"
  description="Use it for a format, a limit, or why we ask. Leave it out when the label says enough."
>
  <Guideline.Do
    width={64}
    example={
      <Field>
        <Field.Label>Mobile number</Field.Label>
        <Field.Input type='tel' />
        <Field.HelperText>We text your tickets to this number.</Field.HelperText>
      </Field>
    }
  >
    Say why we ask, or the format that works.
  </Guideline.Do>
  <Guideline.Dont
    width={64}
    example={
      <Field>
        <Field.Label>Mobile number</Field.Label>
        <Field.Input type='tel' />
        <Field.HelperText>Enter your mobile number.</Field.HelperText>
      </Field>
    }
  >
    Don't repeat the label.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="A placeholder is an example value"
  description="A placeholder disappears as the reader types, so anything they need to remember goes in the label or the helper text."
>
  <Guideline.Do
    width={64}
    example={
      <Field>
        <Field.Label>Event URL</Field.Label>
        <Field.Input placeholder='ochre-kite-weekender' />
        <Field.HelperText>Use lowercase letters and hyphens.</Field.HelperText>
      </Field>
    }
  >
    Show a value the reader could type, and put the rule in the helper text.
  </Guideline.Do>
  <Guideline.Dont
    width={64}
    example={
      <Field>
        <Field.Label>Event URL</Field.Label>
        <Field.Input placeholder='Use lowercase letters and hyphens' />
      </Field>
    }
  >
    Don't put the instructions where they vanish on the first keystroke.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="A choice says what happens when it's ticked"
  description="Write a checkbox or switch label as a positive statement of what the reader gets."
>
  <Guideline.Do example={<Checkbox label='Email me when tickets go on sale' />}>
    Ticking the box turns the thing on.
  </Guideline.Do>
  <Guideline.Dont example={<Checkbox label="Don't stop sending me emails" />}>
    Don't make the reader untangle a negative to know which way to tick.
  </Guideline.Dont>
</Guideline>

</Guidelines>

## Errors

An error says what went wrong and how to fix it, next to the problem.
[Field.ErrorText](/components/field) holds an error in a value, and a
[Callout](/components/callout) holds one about a page or a step. The
[error text guideline](/content/language-and-grammar#guidelines) on Language
and grammar sets its shape: a whole sentence with a full stop.

### Lead with the fix

Start with what to do, because the reader can see which field it's on. When
the value looks right but isn't, such as an expired code, say what's wrong
first.

<PairTable>

| Write                                    | Not                             |
| ---------------------------------------- | ------------------------------- |
| Enter an email address.                  | Email is required.              |
| Enter a mobile number like 0400 000 000. | Invalid phone number            |
| Choose at least 1 ticket.                | Quantity must be greater than 0 |
| Choose a date after today.               | Date is in the past.            |

</PairTable>

<Guidelines>

<Guideline
  headingLevel={3}
  title="Don't blame the reader"
  description="Describe the problem and the fix, not the reader's mistake."
>
  <Guideline.Do
    width={64}
    example={
      <Field invalid>
        <Field.Label>Access code</Field.Label>
        <Field.Input defaultValue='KITE2025' />
        <Field.ErrorText>This code has expired. Ask the promoter for a new one.</Field.ErrorText>
      </Field>
    }
  >
    Say what's wrong with the code and where to get one that works.
  </Guideline.Do>
  <Guideline.Dont
    width={64}
    example={
      <Field invalid>
        <Field.Label>Access code</Field.Label>
        <Field.Input defaultValue='KITE2025' />
        <Field.ErrorText>You entered an expired code.</Field.ErrorText>
      </Field>
    }
  >
    Don't make the error about what the reader did.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="Own the errors that are ours"
  description={`When Oztix fails, say "we", say what's safe, and give the next step. Leave error codes for the support team.`}
>
  <Guideline.Do
    width={72}
    example={
      <Callout intent='danger' title="We couldn't save your changes">
        Your edits are still on this page. Try again in a minute.
      </Callout>
    }
  >
    Take the blame, and tell the reader their work isn't lost.
  </Guideline.Do>
  <Guideline.Dont
    width={72}
    example={
      <Callout intent='danger' title='Error 500'>
        An unexpected error occurred.
      </Callout>
    }
  >
    Don't show a code and a sentence that says nothing.
  </Guideline.Dont>
</Guideline>

</Guidelines>

## Empty states

An [EmptyState](/components/empty-state) says why there's nothing here and
what the reader can do about it.

### Say why it's empty

A title names what's missing. A list that has never had anything, and one a
filter or search has emptied, need different words.

<PairTable>

| Write                        | Not                 |
| ---------------------------- | ------------------- |
| No events yet                | Nothing to see here |
| No events match your filters | 0 results           |
| No orders to refund          | Empty               |

</PairTable>

<Guidelines>

<Guideline
  headingLevel={3}
  title="Give the next step"
  description="Put the action that fills the space on a button, and say in the description what it does."
>
  <Guideline.Do
    example={
      <EmptyState size='sm'>
        <EmptyState.Title>No ticket types yet</EmptyState.Title>
        <EmptyState.Description>Add a ticket type to start selling.</EmptyState.Description>
        <EmptyState.Actions>
          <Button>Add ticket type</Button>
        </EmptyState.Actions>
      </EmptyState>
    }
  >
    Point the reader at the one thing that fills the page.
  </Guideline.Do>
  <Guideline.Dont
    example={
      <EmptyState size='sm'>
        <EmptyState.Title>No data</EmptyState.Title>
        <EmptyState.Description>There's nothing here.</EmptyState.Description>
      </EmptyState>
    }
  >
    Don't leave the reader at a dead end.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="Say when a filter emptied the list"
  description="When a filter or search hides everything, say so, and offer the way back."
>
  <Guideline.Do
    example={
      <EmptyState size='sm'>
        <EmptyState.Title>No events match your filters</EmptyState.Title>
        <EmptyState.Actions>
          <Button>Clear filters</Button>
        </EmptyState.Actions>
      </EmptyState>
    }
  >
    The reader knows the events still exist.
  </Guideline.Do>
  <Guideline.Dont
    example={
      <EmptyState size='sm'>
        <EmptyState.Title>No events yet</EmptyState.Title>
        <EmptyState.Actions>
          <Button>Create event</Button>
        </EmptyState.Actions>
      </EmptyState>
    }
  >
    Don't suggest the events are gone when a filter is hiding them.
  </Guideline.Dont>
</Guideline>

</Guidelines>

## Confirmations

A confirmation asks before something that costs money or can't be undone.
[Dialog](/components/dialog) with `role='alertdialog'` holds it.

<Guidelines>

<Guideline
  headingLevel={3}
  title="Ask about the thing by name"
  description="The title is a question with the action and the thing it acts on."
>
  <Guideline.Do code={`<Dialog.Title>Delete Ochre Kite Weekender?</Dialog.Title>`}>
    The reader knows what's at stake before reading on.
  </Guideline.Do>
  <Guideline.Dont code={`<Dialog.Title>Are you sure?</Dialog.Title>`}>
    Don't make the reader hunt through the body for what they're agreeing to.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="Say what happens next"
  description="The description says who it affects, and whether it can be undone, in a sentence or two."
>
  <Guideline.Do
    code={`
      <Dialog.Description>
        Fans who bought tickets get a refund. You can't undo this.
      </Dialog.Description>`}
  >
    Name who it affects and say plainly that it's final.
  </Guideline.Do>
  <Guideline.Dont
    code={`
      <Dialog.Description>
        This action cannot be undone. Do you wish to proceed?
      </Dialog.Description>`}
  >
    Don't warn without saying what's lost.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="Repeat the action on the button"
  description="The confirming button uses the title's verb. When that verb is cancel, the other button says what staying put means."
>
  <Guideline.Do
    example={
      <Guideline.Row>
        <Button>Keep event</Button>
        <Button intent='danger' emphasis='strong'>Cancel event</Button>
      </Guideline.Row>
    }
  >
    Each button says what it does, even when the action is to cancel.
  </Guideline.Do>
  <Guideline.Dont
    example={
      <Guideline.Row>
        <Button>Cancel</Button>
        <Button intent='danger' emphasis='strong'>OK</Button>
      </Guideline.Row>
    }
  >
    Don't use Cancel and OK when the action is to cancel something.
  </Guideline.Dont>
</Guideline>

</Guidelines>

## Toasts

A [Toast](/components/toast) confirms something the reader just did, or
reports how background work finished. The Toast page says when to use one.

### Say what happened

The title names the thing and what happened to it, in the past tense. Leave
out "successfully" and the exclamation mark.

<PairTable>

| Write               | Not                              |
| ------------------- | -------------------------------- |
| Event published     | Success!                         |
| Link copied         | Copied to clipboard successfully |
| 2 tickets sent      | Your request has been processed  |
| Ticket type deleted | Item removed                     |

</PairTable>

<Guidelines>

<Guideline
  headingLevel={3}
  title="Name the action for what it does"
  description="A toast's one action is a verb, usually Undo or View."
>
  <Guideline.Do
    code={`
      toast.add({
        title: 'Ticket type deleted',
        timeout: 8000,
        actionProps: { children: 'Undo', onClick: undo }
      })`}
  >
    The reader can reverse it in one press.
  </Guideline.Do>
  <Guideline.Dont
    code={`
      toast.add({
        title: 'Ticket type deleted',
        timeout: 8000,
        actionProps: { children: 'Click here', onClick: undo }
      })`}
  >
    Don't make the reader guess what the button does.
  </Guideline.Dont>
</Guideline>

<Guideline
  headingLevel={3}
  title="A failure says what to do"
  description="A danger toast follows Errors. The title names what failed, and the description gives the fix."
>
  <Guideline.Do
    code={`
      toast.add({
        title: "We couldn't export your orders",
        description: 'Try again in a minute.',
        intent: 'danger'
      })`}
  >
    Name what failed and the next step.
  </Guideline.Do>
  <Guideline.Dont
    code={`
      toast.add({
        title: 'Error',
        description: 'Something went wrong.',
        intent: 'danger'
      })`}
  >
    Don't report a failure the reader can't act on.
  </Guideline.Dont>
</Guideline>

</Guidelines>
