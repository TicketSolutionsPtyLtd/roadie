A table of records to search, filter, sort, and page through.

## Import

```tsx
import { RecordTable, shownColumns, tableColumns, tableLayout } from '@oztix/roadie-components/record-table'
import { Records, downloadCsv, useRecords } from '@oztix/roadie-components/records'
import { recordFields, recordsToCsv } from '@oztix/roadie-core/records'
```

Columns with a `cell`, `getRowId`, and the `useRecords` instance hold functions, so they can't pass from a Server Component. Build them and render the table in a client component, a file that starts with `'use client'`.

## Examples

### Default

Describe the records once as fields, pick the fields to show as columns, and pass both with the data. Search, sorting from the headers, and paging come built in.

Search matches every word, in any order, in the text fields and the option labels of fields marked `searchable`. Text fields are searchable by default; other types aren't.

```tsx-live-noinline
const cities = ['Brisbane', 'Melbourne', 'Sydney', 'Perth', 'Hobart']
const names = ['Ocean Alley', 'Ball Park Music', 'Julia Jacklin', 'Angie McMahon', 'Alex Lahey', 'Middle Kids']
const shows = Array.from({ length: 240 }, (_, index) => ({
  id: `show-${index}`,
  show: `${names[index % names.length]} at Kazoo Hollow Room`,
  location: cities[index % cities.length],
  sold: (index * 37) % 2400,
  gross: (index * 7919) % 250000
}))

const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  field.location('location', { label: 'Location' }),
  field.number('sold', { label: 'Sold' }),
  field.money('gross', { label: 'Gross', format: 'compactCurrency' })
]

const column = tableColumns(fields)
const columns = [
  column.field('show', { pin: true }),
  column.field('location'),
  column.field('sold'),
  column.field('gross')
]

render(
  <RecordTable
    caption='Upcoming shows'
    data={shows}
    fields={fields}
    columns={columns}
    getRowId={(row) => row.id}
  />
)
```

In TypeScript, give the builders your row type so every key is checked: `recordFields<Show>()` and `tableColumns<Show>(fields)`.

### States

Pass `loading` while records load and `error` when the load fails. With no records yet, `loading` shows still placeholder rows; with records, it dims them and runs a bar under the header. An error replaces the rows, and `onRetry` adds a Retry button. With no records, the empty state says whether none exist yet or none match, and offers to clear the search and filters.

```tsx-live-noinline
const field = recordFields()
const fields = [field.text('show', { label: 'Show' }), field.location('location', { label: 'Location' }), field.number('sold', { label: 'Sold' })]
const column = tableColumns(fields)
const columns = [column.field('show', { pin: true }), column.field('location'), column.field('sold')]
const shows = [
  { id: 'a', show: 'Ocean Alley', location: 'Brisbane', sold: 1840 },
  { id: 'b', show: 'Alex Lahey', location: 'Melbourne', sold: 920 }
]
const props = {
  fields,
  columns,
  getRowId: (row) => row.id,

}

render(
  <div className='grid gap-8'>
    <div className='grid gap-2'>
      <p className='text-sm text-subtle'>Loading, no records yet</p>
      <RecordTable {...props} caption='Loading shows' data={[]} loading defaultPosition={{ pageSize: 3 }} />
    </div>
    <div className='grid gap-2'>
      <p className='text-sm text-subtle'>Loading, with records</p>
      <RecordTable {...props} caption='Refreshing shows' data={shows} loading />
    </div>

      <p className='text-sm text-subtle'>Empty</p>
      <RecordTable {...props} caption='No shows' data={[]} />

      <p className='text-sm text-subtle'>No match</p>

    </div>
  </div>

```

### Composition

`RecordTable` is `useRecords` and the `Records` parts put together. Build it from the parts to put controls where the screen needs them. `Records.Content` shows the view's layout, here the table from `tableLayout(columns)`.

```tsx
const layouts = [tableLayout(columns)]

function Shows() {
  const records = useRecords({ data, fields, getRowId: (row) => row.id })
  return (
    <Records records={records} layouts={layouts} caption='Upcoming shows'>
      <Records.Header searchPlaceholder='Search shows' />
      <Records.Content />
      <Records.Pagination pageSizes={[20, 40]} />
      <Records.Status />
    </Records>
  )
}
```

`Records.Header` holds the standard controls: the search and filter field, `Records.Select` for Select mode on narrow rows, with `viewActions` the [saved view's actions](#saved-views) as `Records.ViewActions`, `Records.Options`, and with `actions`, the table actions as `Records.Actions` at the end. `searchLabel` names the search when its placeholder doesn't. Pass children to replace them, such as a `Records.Search` with your own placeholder or `aria-label` beside other controls. Keep a table's search with its table, in its header, never in `Pane.Search`.

In a header under 40rem, the search takes the whole row while it has focus. The other controls hide from sight and screen readers, and come back once focus leaves the search. Tab out of the search shows them first, so it lands on the next one.

`Records.BulkActions` can sit anywhere inside the Provider: the table's `Records.Content` shows it in its header row.

### In a Pane

Most record tables live in a [`Pane`](/components/pane). Wrap the pane in `Records.Provider`, which shares the records without adding an element, and spread the parts across it:

- `Records.Header` in `Pane.Body`, above the table. It sticks under the pane's header while the body scrolls, so the search stays in reach, and paints the pane's margins beside it so rows never show there. `Pane.Header` keeps the `Pane.Title`.
- `Records.Content` in `Pane.Body`, below the header. Its column headers stick under the header. Placed straight in `Pane.Body`, a wide table runs to the pane's edges, with the pane's inset inside its first and last cells, so its first column lines up with the search and columns scrolled sideways pass under any pinned ones. Narrow rows, a `fill` or `maxHeight` box, and a pane with a `measure` keep the inset.
- `Records.Status` anywhere inside the Provider. It renders nothing visible.
- `Records.Pagination` in `Pane.Footer`, which stays pinned at the bottom. The table's sideways scrollbar sits just above the footer.
- `Records.BulkActions` anywhere inside the Provider. The table's `Records.Content` shows it in place of the column headers while records are selected, and floats it over narrow rows.

On a phone the table turns into cards: the event, its venue, and its status, with the start, sold, and gross as details. The second frame shows it at 390px. See [Narrow layouts](#narrow-layouts).

### Fields and columns

A field describes one fact about a record, and its type decides how the value reads everywhere it shows:

| Field type | Reads as |
| --- | --- |
| `text` | The text. A list joins with commas. |
| `option` | Each value's label from `options`. With a `status` map, a small Badge in the key's intent. |
| `location` | A place, such as a city: each value's label from `options`, as an option reads. |
| `number` | Its `format`, `number` by default. Figures end-align. |
| `money` | Its `format`, `currency` by default. `currency` or `currencyKey` names a currency that isn't dollars. |
| `date` | House formats: event and access dates in the venue's zone from `timeZoneKey`, timestamps in the reader's zone, a range when the field has an `end`. |
| `boolean` | Yes or No. |

A record that holds nothing for a field shows "Not available". Text a field can't read shows as given: "To be announced" in a date field, or "On sale soon" in a number or money field, which also takes a quieter colour.

A header sorts by its field alone: words A to Z first, figures and dates largest or latest first, and a second click flips it. A field with `sortable: false` has no sort button.

A column presents one field. `tableColumns(fields).field(key, options)` takes:

- `pin` to hold the column at the start while the table scrolls sideways. The column with `narrow: 'title'`, or else the first pinned text column, or else the first text column, is the row's title, in strong text. A custom `cell` there inherits it.
- `width` as `{ min, grow }` in rem, when the content's own width doesn't suit. Without it, each column sizes from a sample of its values.
- `cell` to render the value yourself, such as an order number in `font-mono`. The column sizes from the field's text and reserves no room for an empty value, since your cell draws its own. If it falls back to `RecordValue`, which reads "Not available", give the column a `width`.
- `kind: 'image'` to show the value, an image URL, as a 40px thumbnail, with `alt` to describe it from the row. Its header is read to screen readers but not shown, and it never sorts from there; give its field `searchable: false` and `sortable: false`. A record without an image shows a neutral tile with an image icon.
- `priority` to hide the column as the table narrows. See [Column priority](#column-priority).
- `narrow` to place the column when the table turns into list rows or cards. See [Narrow layouts](#narrow-layouts).

The view's `layout.columns` orders and hides columns: `order` lists keys to bring forward and `hidden` lists keys to leave out. Pinned columns stay first and shown whatever the view says.

### Search and filters

The header's search is a [query field](/components/query-field) named "Search and filter". It searches the records as you type and adds filters as chips. A record shows only when it matches every chip.

```tsx-live-noinline
const field = recordFields()
const places = [
  { value: 'au', label: 'Australia', kind: 'country' },
  { value: 'au-qld', label: 'Queensland', kind: 'state', parent: 'au' },
  { value: 'au-qld-brisbane', label: 'Brisbane', kind: 'city', parent: 'au-qld' },
  { value: 'au-qld-fortitude-valley', label: 'Fortitude Valley', kind: 'suburb', parent: 'au-qld-brisbane' },
  { value: 'au-qld-west-end', label: 'West End', kind: 'suburb', parent: 'au-qld-brisbane' },
  { value: 'au-vic', label: 'Victoria', kind: 'state', parent: 'au' },
  { value: 'au-vic-melbourne', label: 'Melbourne', kind: 'city', parent: 'au-vic' },
  { value: 'au-vic-fitzroy', label: 'Fitzroy', kind: 'suburb', parent: 'au-vic-melbourne' },
  { value: 'au-vic-st-kilda', label: 'St Kilda', kind: 'suburb', parent: 'au-vic-melbourne' }
]
const fields = [
  field.text('show', { label: 'Show' }),
  field.location('location', { label: 'Location', options: places }),
  { ...field.option('venue', { label: 'Venue' }), icon: <BuildingsIcon weight='bold' /> },
  field.option('status', {
    label: 'Status',
    status: { on_sale: { intent: 'success', order: 1 }, selling_fast: { intent: 'warning', order: 2 }, sold_out: { intent: 'danger', order: 3 } }
  }),
  field.date('starts', { label: 'Start date', moment: 'date' }),
  field.number('sold', { label: 'Sold' })
]
const column = tableColumns(fields)
const columns = [
  column.field('show', { pin: true }),
  column.field('location'),
  column.field('venue'),
  column.field('status'),
  column.field('starts'),
  column.field('sold')
]
const bands = ['Ocean Alley', 'Ball Park Music', 'Julia Jacklin', 'Angie McMahon', 'Alex Lahey', 'Middle Kids']
const venues = [
  ['au-qld-fortitude-valley', 'Kazoo Hollow Room'],
  ['au-vic-fitzroy', 'Echidna Gaslight Theatre'],
  ['au-qld-west-end', 'Iguana Teapot Hall'],
  ['au-vic-st-kilda', 'Saltbush Trumpet Ballroom']
]
const statuses = ['on_sale', 'selling_fast', 'sold_out']
const today = plainDateOf(new Date(), viewerTimeZone())
const shows = Array.from({ length: 60 }, (_, index) => ({
  id: `show-${index}`,
  show: bands[index % bands.length],
  location: venues[index % venues.length][0],
  venue: venues[index % venues.length][1],
  status: statuses[index % statuses.length],
  starts: addDays(today, index % 45),
  sold: (index * 137) % 2400
}))

render(
  <RecordTable
    caption='Upcoming shows'
    data={shows}
    fields={fields}
    columns={columns}
    getRowId={(row) => row.id}
    defaultView={{
      query: {
        filters: [
          { field: 'status', operator: 'is', values: ['on_sale', 'selling_fast'] },
          { field: 'location', operator: 'is', values: ['au-qld-brisbane'] }
        ]
      }
    }}
    defaultPosition={{ pageSize: 10 }}
  />
)
```

Each show holds its suburb, and a location's places nest, so the example's "Location is in Brisbane" chip shows the shows in Fortitude Valley and West End, and "Location is in Queensland" would too. Remove the chip, or change it to **is not in**, to see the rest. [Places](/foundations/records#places) covers how they nest.

#### Searching

Typing searches the searchable fields, and suggests the filters the text reads:

- an option's or location's values, or a status
- a boolean, by its name
- an identifier, by its `match`
- a date phrase for each date field, such as "this weekend" or "after 1 dec"

Pick a suggestion with the arrows and Enter, or a click, to add its chip. Enter with no suggestion picked searches the text. A filter takes only the words it reads, and the rest stay in the field for the next one. Typing "melb this weekend" offers "Location is in Melbourne" and "Start date is this weekend".

#### Picking a field

Focus the empty field to list the fields to filter by. Pick one, and the list shows its values under a toggle of operators. Press an operator, or press Tab and Shift+Tab, to change it.

| Field            | Operators                                         | Values                                                                                                  |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Option or status | is, is not, and has all of for a `multiple` field | Its `options`, or up to 1,000 values its records hold. Past that, or when a server filters the records, you type the value. |
| Location         | is in and is not in, which take in every place inside | Its places, each with where it is, such as "Suburb in Brisbane". Without `options`, its records' values, as an option's. |
| Text             | contains, doesn't contain, is, and is not         | What you type                                                                                           |
| Number or money  | `=`, `≠`, `<`, `>`, and between                   | What you type                                                                                           |
| Boolean          | is                                                | Yes and No                                                                                              |
| Date             | is relative, is, is before, is after, and is between | Under is relative, quick dates, upcoming for an event date and recent for a timestamp. Under the others, a calendar |

Every field you can filter by ends its toggle with **is empty** and **is not empty**. A field that holds a list of dates can't be filtered yet, so it isn't listed.

#### Typing a value

- Typing narrows an option, location, boolean, or date field's values, and Enter takes the first.
- Text or a number you type shows as one row worded as its chip, such as "Sold is more than 1,500", and Enter takes it.
- Between reads 20 and 50, 20-50, 20 to 50, or 20..50, in either order. A space after the first number adds the "and", and one Backspace takes it away.
- Money takes a `$` and thousands commas, such as $1,500.
- Until the value reads, the list says what to type, such as "Type a number." or "Between 20 and what? Type the second number."
- Under **is empty** or **is not empty**, the list shows one row, such as "Location is empty", and Enter takes it. What you'd typed is set aside, and comes back if you move to another operator, or press Backspace in the empty field, which also returns to the operator you typed it under. Typing switches back to the field's first operator, such as **is**, so what you type applies.

Another option value taken under **is** joins that field's is chip, which matches any one of its values. An **is empty** chip takes the place of the field's other chips, and any other chip on the field takes the place of its **is empty** chip, as together they match nothing. A date chip takes the place of the field's earlier date chip, as two dates rarely overlap.

#### Editing a chip

Click a chip, or press Enter on it, to edit it in the list. It turns back into a dashed chip in its place, with its value in the field and selected, so typing replaces it. The toggle shows the chip's operator, and the list ticks what the chip holds.

- **An option or location chip.** Its values stay in the dashed chip, and the field is empty. Take values to tick and untick them, and the list stays open for more. Unticking the last value removes the chip. Enter on typed text only ticks. Press **is**, **is not**, or **has all of** (**is in** or **is not in** on a location) to change the condition and keep the values. A chip changed to **is** joins the field's is chip.
- **A text or number chip.** Its value is in the field and its condition in the toggle, such as 20 and 50 under **between**. Change either, and Enter replaces the chip once the value reads and ends the edit.
- **A date chip.** Its dates are in the field, such as 12 Nov to 15 Dec under **is between**, or This week under **is relative**. Type others, or take a quick date or a day from the calendar, to replace them and end the edit.
- **A boolean chip.** The field is empty. Yes or No replaces what the chip holds and ends the edit.
- **Is empty or is not empty.** The row under either replaces what the chip holds, and ends the edit of any chip but an option chip. A chip that already reads is empty or is not empty opens with that row ticked.

Only an option chip changes as you press an operator. Anything else waits for Enter, so pressing Tab past **is empty** keeps the chip's values. Backspace in the empty field removes the chip. Escape, Enter on the chip's value unchanged or with no new value to take, or leaving the field ends the edit and keeps the chip. While you edit, Left and Right move only within the text.

#### Dates

A date field starts on **is relative**, with its quick dates, such as Today, This week, and Next 7 days. Typing narrows them, and phrases like "rest of the month" read too.

Under **is**, **is before**, or **is after**, the dropdown shows a calendar under the values. Click or tap a day to add the chip, such as "Start date is on Thu 22 Oct". Typing suggests days above the calendar, such as Fri for "fri", and Enter takes the first. The calendar moves to the month of the first day, so "26 feb" shows February, and tints the day or range Enter would take. Under **is between**, click two days for a range, or type one, such as "22 oct to 30 oct".

The calendar stays in the dropdown at every screen size, as wide as the field. It shows two months side by side where they fit, and one on a phone, with a month and year select to jump further. Until you type, a hint says you can type a date instead. Dates are whole days, on a timestamp field too. Editing a date chip opens it on its operator, with the calendar on its month and its day or range marked. Picking another day changes the chip.

#### Chips

- A chip with more values than it shows names them all in its tooltip.
- A relative date chip, such as "Start date is this weekend", shows its dates in its tooltip.
- A filter these fields can't apply shows in warning colours and filters nothing.

#### Keys

| Key            | What it does                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/`            | Focuses the search from anywhere on the page, except while you type in another field.                                                                                          |
| Enter          | Takes the suggestion you moved to. With none, it takes an identifier the text matches, or searches the text. While you pick a value, it takes the first value once you type, or the one row under is empty or is not empty. While you edit a chip, with its value unchanged or no new value to take, it ends the edit. |
| Tab, Shift+Tab | While a field's values show, moves to the next or previous operator. From the last operator, or the first, it leaves the input and ends picking a value or editing a chip. |
| Backspace      | In the empty field, selects the last chip, and a second removes it. While you pick a value, it goes back to the fields, and while you edit a chip, it removes that chip.              |
| Escape         | Ends picking a value or editing a chip, and keeps the chips, as leaving the field does. Otherwise it closes the suggestions, then clears the text.                              |

With several searches on a page, the first one takes `/`. Set `searchFocusShortcut` on `RecordTable` or `Records.Header`, or `focusShortcut` on `Records.Search`, to another key, a `KeyboardEvent.key` value such as `s`, or `false`.

#### Scope

A page that shows part of a list, such as one venue's shows or one event's tickets, passes `scope`: filters the page sets, not the person. They show first as locked chips with a "Set by this page" tooltip, and filter the records along with the view.

The scope is never part of the view. Saved views and the URL leave it out. Clear, and the empty state's Clear search and filters, keep it. A list filtered only by its scope counts as unfiltered.

In server mode, fetch `records.request`. Its query is the applied query with the scope's filters first, as is `records.scopedQuery`, and `toMeilisearch` reads it as it is. Table and bulk actions get the same query and request, so an action on every match stays within the page.

A scope holds any filter a field can apply. An app turns a rule such as "products on this event, its days, or its collection" into filters on its own fields.

```tsx-live-noinline
const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  { ...field.option('venue', { label: 'Venue' }), icon: <BuildingsIcon weight='bold' /> },
  field.number('sold', { label: 'Sold' })
]
const column = tableColumns(fields)
const columns = [column.field('show', { pin: true }), column.field('venue'), column.field('sold')]
const venues = ['Kazoo Hollow Room', 'Opal Harpoon Room', 'Antler Kettle Hall']
const bands = ['Ocean Alley', 'Ball Park Music', 'Julia Jacklin', 'Angie McMahon']
const shows = Array.from({ length: 24 }, (_, index) => ({
  id: `show-${index}`,
  show: bands[index % bands.length],
  venue: venues[index % venues.length],
  sold: (index * 211) % 1800
}))

render(
  <RecordTable
    caption='Shows at Kazoo Hollow Room'
    data={shows}
    fields={fields}
    columns={columns}
    getRowId={(row) => row.id}
    scope={[{ field: 'venue', operator: 'is', values: ['Kazoo Hollow Room'] }]}
  />

```

### Views

A view holds the search, filters, sort, and layout; a position holds the page and page size. Both work uncontrolled, with `defaultView` and `defaultPosition`, or controlled, with `view` and `onViewChange`, and `position` and `onPositionChange`. A change to the search, filters, or sort returns to the first page: when the page changes, `onPositionChange` hears that first, then `onViewChange` gets the view and the new position, so a parent writing both to one URL ends with the two agreeing.

Keep the view in the URL with `recordViewToSearchParams` and `recordViewFromSearchParams`, as [Records model](/foundations/records) shows. A view can name a filter on a field these records don't have, or one its field can't read, such as a date range that ends before it starts. The records skip it, show the rest, list it in `skippedFilters`, and warn in development. A sort on a field that doesn't sort is skipped too, with the same warning, and no header shows it.

```tsx-live-noinline
const field = recordFields()

  location: cities[index % cities.length],
  sold: (index * 37) % 2400
}))

  })
  return (
    <div className='grid gap-3'>
      <p className='text-sm text-subtle'>URL: ?{recordViewToSearchParams(view).toString()}</p>

        caption='Shows'
        data={shows}

        columns={columns}

    </div>

}

render(<Controlled />)
```

### Options

`Records.Options` is the Configure button in the header, after the search and before any table actions, so their More actions menu stays last. It opens a popover below the button, lined up with its end, or a bottom drawer on a phone, and every change applies at once.

- **Sort** lists each level the view sorts by: a field, then its direction in the field's own terms, such as A to Z, Low to high, or Earliest first. Add sort starts with the first sortable field, its natural way, and Add another sort breaks ties with a field not sorted yet. A header click still sorts by that column alone. A level on a field that doesn't sort isn't listed, and changes here leave it in the view. A level that repeats a field sorts nothing, so changes here drop it.
- **Columns** lists the table's columns in their order. Drag a handle to move a column, or click it, or press Enter on it, for a Move menu. The eye beside each column shows or hides it, and a hidden column stays in the list, dimmed, in its place. Pinned columns always come first and always show, so the list names them rather than offering them. The last shown column can't be hidden.

The options write the view, like the headers do: the sort to `query.sort`, and the columns to `layout.columns`, with the whole `order` once a column moves and the `hidden` keys. Put back the way the columns are defined, the layout leaves both out, so `equalRecordViews` reads it as unchanged. A view's keys for columns this table doesn't have, such as one only some people see, are kept. The button shows only when a field sorts or a column can move or hide: two columns that aren't pinned, or one beside a pinned column.


### Saved views

A saved view is a view with a name that people come back to. Apps ship preset views for a screen, such as On sale and Sold out on an events screen, and people save their own beside them. Roadie applies views and tells when one has changed. Your app stores the views and lists them.

Pass the saved view the screen opened as `baseline`. `modified` says whether the view now shows something else, by `equalRecordViews`, which ignores the id, the name, spacing in the search, and the order of chips. `resetView` goes back to the baseline from the first page. The page's `scope` is never part of a view, so it never makes one read as modified.

`viewActions` on `RecordTable` or `Records.Header` takes the handlers below as one object, the props of `Records.ViewActions`, unlike the arrays `actions` and `bulkActions` take. It shows the baseline's name after the search and Select, before Configure, with a dot once the view is modified and a tooltip with the whole name. In your own header, put `Records.ViewActions` in the same place. Its menu offers what your handlers allow:

- **Save view** calls `onSave` with the view under the baseline's id and name. It shows while the view is modified.
- **Reset view** goes back to the baseline. It shows while the view is modified, and needs no handler.
- **Save as new view** asks for a name, then calls `onSaveAs` with the view, that name, and no id, for your app to assign one.
- **Rename view** asks for a new name, then calls `onRename` with the baseline under it. Unsaved changes stay unsaved.
- **Delete view** asks first, then calls `onDelete` with the baseline. Open another view once it resolves.

Leave out the handlers a view doesn't allow. A preset takes `onSaveAs` alone, so people can start their own view from it but can't change it for everyone. With no baseline, the button reads Unsaved view and offers Save as new view, and a baseline with no name reads Untitled view. A baseline with nothing to offer still shows its name, in a button that opens nothing, so focus stays put after a reset. With neither a baseline nor `onSaveAs`, it renders nothing.

Names are asked for in a dialog, or a bottom drawer on a phone, and Delete view asks in an alert dialog on every screen. A handler can return a promise, and the button or the dialog's action stays busy until it settles. Reject to say it failed. The dialog stays open and shows the error's message, so reject with one people can read, such as "You already have a view called Perth". Without a message it says plainly that the view wasn't saved, renamed, or deleted. While a handler runs, the dialog stays open. A failed Save view goes to `reportError`, so show your own toast too.

Keep the open view in the URL. `recordViewToSearchParams` writes its id as `view`, so a link opens the same view with the same changes. A link to a saved view as it is can carry its id alone, `?view=on-sale`, which `recordViewFromSearchParams` reads as no view, so pass that saved view as the fallback. Then find the baseline by the view's id:

```tsx
const saved = [...presets, ...myViews]
const opened = saved.find((held) => held.id === searchParams.get('view')) ?? presets[0]
const { view } = recordViewFromSearchParams(searchParams, fields, { fallback: opened })
const baseline = saved.find((held) => held.id === view.id)
```

### Selection and actions

`bulkActions` turns on a checkbox for each record and shows the bulk actions once something is selected. An action gets the selection and the query and request it was taken against: the picked ids, or every matching record but some. It never gets a record the search and filters hide. Selection is session state, like the page, and works controlled with `selection` and `onSelectionChange` or uncontrolled with `defaultSelection`. A search or filter change drops picked records it hides, and drops a "select all".

`rowActions` returns menu items for a record, shown in a menu on its row named "More actions for" the record. `getRowHref` links each record to its page through the title column. The title stays in strong text and underlines on hover, as a `DataTable` title does. A long title wraps onto a second line, linked or not, and is cut short there so the row keeps its height. Other values stay on one line, and a custom `cell` in the title column lays itself out. When records can be selected, clicking anywhere else on a row selects it, and Shift extends the selection from the last one picked; otherwise the click follows the link. Cmd or Ctrl opens the record in a new tab. Return `undefined` for a record with no page.

While records are selected, the bulk actions take the column headers' place in the same sticky row, so the rows never move and the bar stays in view as the table scrolls down or sideways. The page checkbox stays at the start. The count, such as "3 selected", opens a menu with Clear selection, and with "Select all" once the whole page is checked and more records match. Actions follow as buttons, and those that don't fit move into a More actions menu at the end. The headers come back once the selection clears. Danger actions ask first unless `confirm` is `false`, and any other action asks when given `confirm`.

### Table actions and export

`actions` act on everything the search and filters match, with nothing selected, such as exporting an attendee list. Each gets the applied query, the request for every match, and the records. The first shows as a button at the end of the header and the rest sit in a "More actions" menu after it. In a header under 40rem they all sit in the menu. Danger actions confirm first, as bulk actions do. They stay in the header while records are selected, apart from the bulk actions in the header row, so it stays clear which actions use the selection.

`recordsToCsv(rows, fields, { timeZone })` from `@oztix/roadie-core/records` writes rows as CSV, one column per field, each value as the table shows it, and `downloadCsv` saves it. In the browser, `records.matchingRows` holds every matching record in the current sort, across pages, and `shownColumns(columns, records.view.layout)` gives the columns the table shows, in its order. Pass `{ values: 'raw' }` to write plain numbers a spreadsheet can sum. Text that starts like a formula, such as `=` or `@`, is written with a leading apostrophe so a spreadsheet shows it rather than runs it. A column with its own `cell` exports its field's value, not what your cell draws.

```tsx-live-noinline

const columns = fields.map((field, index) => column.field(field.key, { pin: index === 0 }))
const exportCsv = (records) =>
  downloadCsv(
    recordsToCsv(
      records.matchingRows.map(({ row }) => row),
```

An action gets one object: `query`, the applied query with the scope first; `request`, that query resolved for a server, with relative dates fixed and no paging, as it means every record that matches; `timeZone` and `now`, the zone and moment `request` resolved in; and `records`. A bulk action gets `selection` in place of `records`.

When the browser doesn't hold every record, POST `request` and export on the server with the same fields. [Records model](/foundations/records#server-contract) has the request's shape. Have the server send the CSV without a byte order mark, since `downloadCsv` adds one.

```tsx

      const response = await fetch('/api/attendees/export', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },

      })
      downloadCsv(await response.text(), 'attendees.csv')

```

### Totals

`totals` adds a row of totals under the headings, over every record the search and filters match, not just the page. It reads "Totals for 1,234 shows" from `recordName` and the count, in the title column that carries the row link, and changes as people search and filter. With no title column, the label takes the first column without a sum that isn't an image, as on a DataTable. Use it when the totals belong to columns people read down. For two or three headline numbers, show StatTiles above the table instead.

`totals` (or `'sum'`) adds up the number and money fields in the browser. Shares, indexes, and points don't add up, so they stay blank, and so does money whose rows name their own currency through `currencyKey`. Give a column `total: false` to leave it blank too, as for an id held as a number. On a RecordTable column it only hides the total, which `records.totals` still holds; on a DataTable column it leaves the column out of the sum. Each total reads in its field's format.

### Server data

Pass `rowCount` and the records stop searching, filtering, sorting, and paging in the browser. `data` is one page, in the order the server returned it, and `rowCount` counts every record that matches. `onRequestChange` hands you the request to fetch once the page hydrates, then each time the view, position, zone, or `now` changes it. It carries the page, relative dates such as "today" fixed in the viewer's zone, the page's `scope` first, and only the filters and sorts the fields can apply, as the table shows them. From `useRecords`, `records.request` holds the same. The search waits for a 250ms pause in typing before the request or `onViewChange` hears it, so a request doesn't leave on every keystroke. Clearing it is immediate.

Set `loading` until the rows for the latest request arrive. To have it true in the very render where the view or position changes, hold both yourself, usually in the URL, and key `loading` on them. While `loading` or `error` is set, the records keep a page past the old count, so a linked page waits for the new count before it moves, and `Records.Status` waits for the new count before it announces it. Once given, `rowCount` keeps server mode on: left `undefined` while a page loads, it keeps the last count. Pass 0 until the first count arrives. Take each change `onViewChange` reports: a parent that ignores a search leaves the field showing it. Column widths come from the first page a search or filter brings, and hold as people page, so the columns don't shift.

Some backends stop counting, such as a search index that counts to 10,000. Pass `rowCountExact={false}` with the count it stopped at. Counts then read "10,000+": the pagination, Select all, the selection, the status, and the confirm dialog. Paging stops at the last whole page within the count, and a range list's last range ends at the count, so every request is one the server can return.

Selection works against the total. Records ticked on different pages stay selected, and Select all picks `{ allMatching: true, except }`, counted from `rowCount`. A bulk action gets that selection and the query and request it was taken against, so the server acts on the same records. A new search or filter clears the selection, since only the server knows what still matches; a new sort or page keeps it. Selecting needs `getRowId`, as index ids repeat on every page. `matchingRows` holds only the page, so export on the server, as Table actions shows.

This example's server is pretend: it reads the request `onRequestChange` hands over, filters and sorts with core's `compileRecordQuery` and `sortRecords`, as an index would, waits half a second, and shows the request it was sent.

```tsx-live-noinline

const everyShow = Array.from({ length: 400 }, (_, index) => ({
  id: `show-${index}`,
  show: `${names[index % names.length]} ${Math.floor(index / names.length) + 1}`,
  venue: venues[index % venues.length],
  location: cities[index % cities.length],
  status: ['on_sale', 'on_sale', 'sold_out', 'cancelled'][index % 4],
  sold: (index * 37) % 2400
}))

const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  field.text('venue', { label: 'Venue' }),
  field.location('location', { label: 'Location' }),
  field.option('status', {
    label: 'Status',
    status: {
      on_sale: { intent: 'success', label: 'On sale' },
      sold_out: { intent: 'neutral', label: 'Sold out' },
      cancelled: { intent: 'danger', label: 'Cancelled' }
    }
  }),
  field.number('sold', { label: 'Sold' })
]
const column = tableColumns(fields)
const columns = fields.map((field, index) => column.field(field.key, { pin: index === 0 }))
const timeZone = 'Australia/Sydney'

function pretendServer(request) {
  const { query, page, pageSize } = request
  const matching = sortRecords(everyShow.filter(compileRecordQuery(query, fields)), query.sort, fields, { timeZone: query.timeZone })
  const start = page * pageSize
  return new Promise((resolve) =>
    setTimeout(
      () =>
        resolve({
          rows: matching.slice(start, start + pageSize),
          rowCount: matching.length,
          totals: { values: { sold: matching.reduce((sum, show) => sum + show.sold, 0) } },
          request
        }),
      500
    )
  )
}

const firstView = { query: { search: '', filters: [], sort: [] }, layout: { type: 'table' } }

function ServerShows() {
  const [request, setRequest] = useState(null)
  const [result, setResult] = useState({ rows: [], rowCount: 0, request: null })

  useEffect(() => {
    if (!request) return
    let current = true
    pretendServer(request).then((next) => {
      if (current) setResult(next)
    })
    return () => {
      current = false
    }
  }, [request])

  return (
    <div className='grid gap-3'>
      <RecordTable
        caption='Shows'
        data={result.rows}

        totals={result.totals}

        columns={columns}
        getRowId={(row) => row.id}

        defaultPosition={{ pageSize: 25 }}
        onRequestChange={setRequest}
        timeZone={timeZone}
        bulkActions={[{ label: 'Export', onAction: ({ selection, request }) => console.log('export', selection, request) }]}
      />

        <pre className='rounded-md bg-sunken p-3 font-mono text-xs break-all whitespace-pre-wrap text-subtle'>
          {JSON.stringify(result.request)}
        </pre>
      )}
    </div>
  )
}
```

With Meilisearch, `toMeilisearch(request, fields)` from `@oztix/roadie-core/records/meilisearch` turns the request into a search. Its `page` and `pageSize` become `page` and `hitsPerPage`, so the response's `totalHits` counts the matches for `rowCount`. Meilisearch stops counting at the index's `pagination.maxTotalHits`, 1,000 by default, so raise it to the most records a screen can match, or pass `rowCountExact={false}` when `totalHits` reaches it. The request's relative dates are already fixed in the viewer's zone, so the server reads no clock. [Records model](/foundations/records) lists the index shape it needs.

```tsx

const response = await client.index('events').search(q, params)
const page = { rows: response.hits, rowCount: response.totalHits }
```

To build a request away from the table, as for a link or a scheduled export, call `toRecordsRequest(view.query, fields, { now, timeZone, scope }, position)` from `@oztix/roadie-core/records`. It throws for a filter on a field the list doesn't have, where the table skips it, so check a stored view with `validateRecordView` first.

### Range loading

Pass `loadRange` for one long list with no pages that loads the records on screen as people scroll. The list asks for the rows on screen plus a screen either side, a page per request, each a request with `start` and `end`, `end` exclusive, to POST as it is. Each range is one whole page, page `start / pageSize`, so fetch `pageSize` records from `start`; the last one can run past the end of the list, unless the count is one the server stopped at, where it ends at the count. Resolve with `{ rows, rowCount }`: the range's records, in order, and the total that matches, with `rowCountExact: false` when it is a floor. Leave out `data`; the list holds what it loads. Rows that haven't arrived show as grey placeholders.

The server searches, filters, and sorts, as in server mode, and the search waits for a pause in typing. The list keeps each range's records with the request they answer, drops a response for an older one, and starts over when the search, filters, sort, or zone change, or when a new `now` moves a relative date. It keeps the last total until the new query's first response, so the scrollbar holds its length. The first range brings the count, so a list that opens at a saved row asks for the first page, then the row's. A count that grows, as when a record is added at the end, loads the rows it adds. Every request in this example waits 400ms.

If `loadRange` rejects, the range shows an error row in place of its records, with Retry, and the records already loaded stay. When nothing has loaded yet, the table shows its error state instead. Range mode stops at 300,000 rows. With range loading, `Records.Pagination` shows the count instead of pages, such as "1,284 shows", or "50+ shows" while the total is unknown, with no page buttons and no rows per page: the list scrolls. Paging stays for paged tables.

Use range loading for long lists people scroll, open a record and come back to. Use pages when people jump to a known page, or the list is short.

### Narrow layouts

Under 40rem of its own width, 640px at the default text size, the table drops its columns and lists its records. It measures the table, not the screen, so a table in a side panel turns into a list on a wide monitor too. Each column picks its place with `narrow`:

| `narrow` | Where the column goes |
| --- | --- |
| `'title'` | The record's title, in strong text. It carries the record's link. Without one, the pinned text column, then the first text column, is the title. |
| `'description'` | One line under the title, in subtle text. |
| `'leading'` | Before the title. An image column goes here unless you say otherwise. |
| `'trailing'` | At the end of the row, such as a status badge. |
| `'detail'` | A label and value on a card. Any detail column turns the rows into cards. |
| `'hidden'` | Left out of the narrow layout. The default for every column but images. |

The server can't measure the table, so it renders wide, and a phone switches to the list once the page hydrates. List rows reach 12px into the space beside the table, as a `List` does, so their text lines up with the header: give the table at least that much inline padding, as a page or `Pane` does. In a box of its own, with `maxHeight` or `fill`, rows stay inside the box. The examples below sit in a 360px box.

Narrow rows load by range and render only near the screen past 100 records, as wide rows do. The bulk actions float at the foot of the screen, keeping the first action and putting the rest in a More actions menu when they don't fit.

    Put the search in the header above the rows, where it sticks while the
    body scrolls and clearly searches this table.
  </Guideline.Do>
  <Guideline.Dont
    code={`<Pane.Header>
  <Pane.Title>Events</Pane.Title>
  <Pane.Search value={search} onValueChange={setSearch} />
</Pane.Header>`}
  >
    Don't move a table's search into `Pane.Search`. It reads as a search of
    the whole pane.
  </Guideline.Dont>
</Guideline>

<Guideline title='Describe fields once, at module scope'>
  <Guideline.Do
    code={`const field = recordFields<Event>()
export const eventFields = [field.text('name', { label: 'Event' })]
const column = tableColumns<Event>(eventFields)
const columns = [column.field('name', { pin: true })]`}
  >
    Build fields and columns once, outside the component, and share the
    fields with the server, filters, and URLs. Stable arrays keep rows from
    rendering again.
  </Guideline.Do>
  <Guideline.Dont
    code={`function Events() {
  const fields = [{ key: 'name', label: 'Event', type: 'text' }]
  return <RecordTable fields={fields} columns={...} data={events} />
}`}
  >
    Don't rebuild fields or columns on every render. The table resizes its
    columns and renders every row again each time.
  </Guideline.Dont>
</Guideline>

<Guideline title='Pin one title column'>
  <Guideline.Do code={`column.field('name', { pin: true })`}>
    Pin the column that names the record. It stays in view as the table
    scrolls sideways and reads in strong text.
  </Guideline.Do>
  <Guideline.Dont
    code={`column.field('name', { pin: true }),
column.field('venue', { pin: true }),
column.field('location', { pin: true })`}
  >
    Don't pin several columns. Each one takes width from the columns that
    scroll.
  </Guideline.Dont>
</Guideline>

<Guideline title="Set a page's scope, don't add it as a filter">
  <Guideline.Do code={`<RecordTable scope={[{ field: 'venue', operator: 'is', values: [venueId] }]} {...props} />`}>
    Pass what the page is about as `scope`. It shows as a locked chip, and
    Clear, a saved view, and the URL leave it alone.
  </Guideline.Do>
  <Guideline.Dont
    code={`<RecordTable defaultView={{ query: { filters: [{ field: 'venue', operator: 'is', values: [venueId] }] } }} {...props} />`}
  >
    Don't start the view with the page's own filter. People can remove it
    and see records the page isn't about, and saving the view keeps it.
  </Guideline.Dont>
</Guideline>

<Guideline title='Let people copy a preset, not change it'>
  <Guideline.Do
    code={`viewActions={preset ? { onSaveAs } : { onSave, onSaveAs, onRename, onDelete }}`}
  >
    Give a preset Save as new view alone. People make it their own without
    changing the screen's starting point for everyone.
  </Guideline.Do>
  <Guideline.Dont code={`viewActions={{ onSave: savePreset, onSaveAs }}`}>
    Don't let one person save over a preset. Everyone who opens the screen
    then starts from their filters.
  </Guideline.Dont>
</Guideline>

<Guideline title="Keep the whole view in the URL">
  <Guideline.Do code={`router.replace(\`?\${recordViewToSearchParams(view, position)}\`)`}>
    Write the whole view with its id, so a link or a reload opens the same
    view with the same changes, still marked as modified.
  </Guideline.Do>
  <Guideline.Dont code={`router.replace(\`?view=\${view.id}\`)`}>
    Don't write the id alone. A reload loses the changes without a word.
  </Guideline.Dont>
</Guideline>

<Guideline title='Put the More menu last'>
  <Guideline.Do
    code={`actions={[
  { label: 'Export CSV', onAction: exportCsv },
  { label: 'Print door list', onAction: printDoorList }
]}`}
  >
    Lead with the action people use most. It shows as a button, and the rest
    sit in the More actions menu at the end of the header.
  </Guideline.Do>
  <Guideline.Dont
    code={`<Records.Header>
  <Menu>{/* More actions */}</Menu>
  <Records.Search />
  <Button>Export CSV</Button>
</Records.Header>`}
  >
    Don't put a menu before the search or other actions. The More menu
    always comes last in an action group.
  </Guideline.Dont>
</Guideline>

<Guideline title='Let people arrange columns in Configure'>
  <Guideline.Do
    code={`<Records.Header searchPlaceholder='Search events' />`}
  >
    Keep the standard header, or put `Records.Options` after the search in
    your own. People sort, move, and hide columns there, and the view keeps
    it.
  </Guideline.Do>
  <Guideline.Dont
    code={`<Menu>
  <Menu.Trigger render={<Button>Columns</Button>} />
  <Menu.Content>{/* a checkbox per column */}</Menu.Content>
</Menu>`}
  >
    Don't build a separate columns menu. It can't reorder, and its state
    never reaches the view or the URL.
  </Guideline.Dont>
</Guideline>

<Guideline title='Act on the selection the bar shows'>
  <Guideline.Do
    code={`bulkActions={[{
  label: 'Cancel',
  intent: 'danger',
  onAction: ({ selection, request }) => cancel(selection, request)
}]}`}
  >
    Act on the selection and request the action gets. They hold only records
    the search and filters still show, and "all matching" means the query.
  </Guideline.Do>
  <Guideline.Dont
    code={`onAction: () => cancel(mySelectedIds)`}
  >
    Don't keep your own list of ids. It can hold records the search has
    since hidden, which people never confirmed.
  </Guideline.Dont>
</Guideline>

<Guideline title='Let the table show its own states'>
  <Guideline.Do code={`<RecordTable loading={isLoading} error={failed} onRetry={refetch} {...props} />`}>
    Pass `loading`, `error`, and `onRetry`. The table shows the matching
    EmptyState, placeholders, and announcements.
  </Guideline.Do>
  <Guideline.Dont
    code={`{failed ? <p>Something went wrong</p> : <RecordTable {...props} />}`}
  >
    Don't swap the table for your own message. The header and pager
    disappear, and screen readers hear nothing.
  </Guideline.Dont>
</Guideline>

<Guideline title='Load by range when people scroll and come back'>
  <Guideline.Do code={`<RecordTable loadRange={async (request) => ({ rows, rowCount })} {...props} />`}>
    Load by range when the list is long and people scroll it, open a record
    and come back. Return a total with each range, so the scrollbar is honest
    and a restored row lands as soon as the count arrives.
  </Guideline.Do>
  <Guideline.Dont
    code={`<RecordTable data={everyRecord} defaultPosition={{ pageSize: 100000 }} {...props} />`}
  >
    Don't load every record up front to avoid paging. Use pages when people
    jump to a known page or the list is short.
  </Guideline.Dont>
</Guideline>

</Guidelines>

## Accessibility

- `caption` names the table. Wide, every part reads as a table, with column headers and cells. Narrow, the records are a list named by the caption, each an item with its place in the whole list (`aria-posinset` and `aria-setsize`) when the list holds only some of them.
- A sortable column's header is a button. The sorted column carries `aria-sort`.
- When the table scrolls sideways, its frame is a region named "Shows, scrolls sideways" for a caption of Shows, and the scroller is its one tab stop, so keyboard users can scroll it with the arrow keys. In its own box (`maxHeight` or `fill`), the box is the region, named "Shows, scrolls".
- Wide, the totals are a row in the table's head, under the column headers, with its label as the row's header, so each total reads with its column's name. Narrow, they're a paragraph above the list, each total after its heading.
- `Records.Status` is a live region. It announces Loading, the error, and the result count while a search or filter narrows the list.
- When the table holds only some of its rows (a page of several, more than 100 rows, or a list loaded by range), it carries `aria-rowcount`, counting every match (up to 300,000 loading by range), the header row, and the totals row when there is one, and each row its `aria-rowindex`, so screen readers announce "row 52 of 121". Loading by range, the count is `-1` until the total is known.
- Loading by range, the table is `aria-busy` while a range loads, placeholders are hidden from screen readers, and a failed range is announced, such as "Couldn't load more shows". The result count is announced only once the total is known. The header checkbox is named "Select loaded rows".
- State titles are paragraphs, not headings, since the table can't know the page's outline. Their icon tiles are hidden from screen readers.
- The search is a combobox named "Search and filter", or by its `aria-label`. Suggestions open as you type, on a click, or with the arrows, not on Tab. While they're open, the rest of the page is hidden from screen readers, as for any combobox. Clear keeps focus in the field and keeps the page's scope. [Keys](#keys) lists what each key does.
- Chips are a toolbar named "Filters", and Left and Right move between them. Selecting a chip lists its values and keeps focus in the field. Each chip's remove button is named "Remove" and the chip. A locked scope chip says it's set by this page, and a chip's dates, or a note that it can't apply, are read after its label.
- The operators are a toggle group named "Operator". A number's operators are symbols named in words, such as "is less than" for `<`.
- A date's calendar is named after the field, such as "Start date". Focus stays in the field as you press it, and Tab moves through the operators, so the keyboard picks a date by typing it.
- Each record's checkbox is named "Select" followed by the record's title, or its id with no title, and the header checkbox is named "Select page", with a mixed state when only some of the page is checked.
- `Records.Status` also announces the selection, such as "3 selected, 24 results". It announces a search's count once typing settles, not on every keystroke, and against a server once the new count loads.
- While records are selected, the bulk actions are a toolbar named "Bulk actions" in the header row, beside "Select page", which keeps focus as the bar replaces the column headers. The headers stay in the table for screen readers, and the toolbar sits in a last header with no cells under it. Arrow keys move between its controls. Escape clears the selection and returns focus to "Select page".
- Each row's actions menu is named "More actions for" the record's title. Table actions past the first sit behind a button named "More actions". A running action's control stays focusable but disabled, with `aria-busy`. A confirmation is an alert dialog.
- The view button is named "View:" and the view's name, with ", unsaved changes" once the view has changed, as its tooltip shows, and opens a menu. Save view and Reset view sit in a group named "Unsaved changes". Save as new view and Rename view open a dialog of that name with focus in its Name field, the whole name selected to rename, and an empty name says "Enter a name". Delete view asks in an alert dialog. Focus returns to the view button as each closes. While a handler runs, its control stays focusable but disabled, with `aria-busy`.
- The Configure button is named "Configure table", as is the dialog it opens. Given more than one layout, its Layout switcher is a group named "Layout" of toggle buttons, with the shown layout pressed. Its sort controls are named "Sort by", then "Then by, level 2" and so on, and for each level the field's order, such as "Sold order". Adding a level moves focus to its field, and removing one moves focus to the Remove of the level that takes its place, or of the one before it, or to Add sort. Each column's handle is named "Reorder" and the column, its eye is a toggle button named "Show" and the column, pressed while the column shows (the last shown column's is disabled and says why), and each move is announced, such as "Gross moved to position 1 of 4 columns".
- In Select mode, each record's checkbox covers the record, so a tap anywhere on it toggles, and the link steps aside. "Select" and "Done" are one button, which keeps focus as it switches. Select mode's controls are a group named "Select mode", and the floating bulk actions a group named "Bulk actions", where Escape leaves Select mode. When the bar goes, focus lands on Select, or on the records.
- Focus follows the record across a switch between the table and the list, onto the same record's link or first control.
- A row with `getRowHref` holds a real link: it opens in a new tab with Cmd or Ctrl, and works with every other link convention, not just a click handler.

## Hooks

### useRecords

```tsx
function useRecords<Row extends object>(options: UseRecordsOptions<Row>): RecordsInstance<Row>
```

Holds the view, position, and selection, and searches, filters, sorts, and pages the records in the browser, or with `rowCount` leaves that to a server. Takes `data` (left out with `loadRange`), `rowCount`, `rowCountExact` (false when the count is a floor the server stopped at), `fields`, `getRowId`, `view`, `defaultView`, `onViewChange`, `baseline` (the saved view the screen opened), `scope` (the page's own filters), `position`, `defaultPosition`, `onPositionChange`, `selectable`, `selection`, `defaultSelection`, `onSelectionChange`, `rowActions`, `getRowHref`, `recordName`, `loading`, `error`, `onRetry`, `timeZone` (the reader's, which decides what "today" is), `now` (when relative dates resolve, by default when the list mounted in the browser; a server reads no clock, so a relative date filter shows the loading state until then), `loadRange` (which loads the list by range as people scroll, resolving with `{ rows, rowCount, rowCountExact }`), and `onRequestChange` (which hears each request to fetch). Pass the result to `Records` or `Records.Provider`, which take only what `useRecords` returns, not an object built to its shape.

| Field | Type | Description |
| --- | --- | --- |
| `mode` | `'browser' \| 'server' \| 'range'` | Where the records are searched and paged: `server` once `rowCount` is given, `range` once `loadRange` is. |
| `data` | `readonly Row[]` | Every record held, before search, filters, and paging. In server mode, the page; in range mode, the records loaded, in order. |
| `fields` | `readonly RecordsField[]` | What each record holds. |
| `view` | `RecordView` | The search, filters, sort, and layout. |
| `appliedView` | `RecordView` | The view the rows show, without the filters and sorts the fields can't apply, and without the page's scope. In the browser its search lags typing while a long list filters. Its `query` keeps its identity while its content holds. |
| `request` | `RecordsRequest` | What to POST to a server: the applied query with relative dates fixed and the scope first, under `version` 1, with `page` and `pageSize` in server mode. It keeps its identity while its content holds, so key a fetch on it. |
| `rows` | `readonly { id: string; row: Row }[]` | The current page. In range mode, every record loaded. |
| `resultCount` | `number` | Records the search and filters match: `rowCount` in server mode. |
| `resultCountExact` | `boolean` | False when `resultCount` is a floor the server stopped counting at, from `rowCountExact`. |
| `filtered` | `boolean` | Whether a search or filter narrows the records. |
| `position` | `{ page: number; pageSize: number; row: number }` | The page, zero-based, and its size. In range mode, `row` is the first row on screen and each range is one page. |
| `pageCount` | `number` | Pages at this size, at least one. |
| `setView` | `(view: RecordView) => void` | Replaces the view. |
| `baseline` | `RecordView \| undefined` | The saved or preset view the screen opened. |
| `modified` | `boolean` | Whether the view shows something other than `baseline`, by `equalRecordViews`. Always false without one. |
| `resetView` | `() => void` | Goes back to `baseline` from the first page. Does nothing without one. |
| `skippedFilters` | `readonly number[]` | Filters in the view, by index, that these fields can't apply. |
| `scope` | `readonly RecordFilter[]` | The page's own filters, applied before the view's and never part of it. |
| `scopedQuery` | `RecordQuery` | The applied view's query with the scope's filters first, which actions get as `query`. It keeps its identity while its content holds. |
| `setSearch` | `(search: string) => void` | Sets the search and returns to the first page. In server mode, once typing pauses for 250ms, or at once when cleared. |
| `addFilter` | `(filter: RecordFilter) => void` | Adds a filter. |
| `updateFilter` | `(index: number, filter: RecordFilter) => void` | Replaces the filter at an index. |
| `removeFilter` | `(index: number) => void` | Removes the filter at an index. |
| `clearQuery` | `() => void` | Clears the search and filters, keeping the sort and layout. |
| `setSort` | `(sort: RecordSort[]) => void` | Sets the sort and returns to the first page. |
| `setLayout` | `(layout: RecordLayout) => void` | Sets the layout, such as the table's column order. |
| `setPage` | `(page: number) => void` | Goes to a page, within the pages there are. |
| `setPageSize` | `(pageSize: number) => void` | Sets the page size and returns to the first page. |
| `matchingRows` | `readonly { id: string; row: Row }[]` | Every record the search and filters match, sorted, across pages. In server mode, only the page. |
| `selectable` | `boolean` | Whether records can be selected. |
| `selection` | `RecordSelection` | `{ ids }`, or `{ allMatching: true, except }`. |
| `selectedCount` | `number` | Selected records the search and filters still match. In server mode, the ids picked, or `rowCount` less the exceptions. |
| `isSelected` | `(id: string) => boolean` | Whether a record is selected. |
| `countSelection` | `(selection: RecordSelection) => number` | How many records a selection holds that the search and filters still match. In server mode, the ids picked, or `rowCount` less the exceptions. |
| `setSelection` | `(selection: RecordSelection) => void` | Replaces the selection. |
| `toggleRow` | `(id: string, options?: { range?: boolean }) => void` | Picks or drops a record; `range` covers every record from the last one toggled, in sorted order. |
| `selectPage` | `(value: boolean) => void` | Picks or drops every record on the page. |
| `selectAllMatching` | `() => void` | Picks every record the search and filters match. |
| `clearSelection` | `() => void` | Drops the selection. |
| `setSelecting` | `(value: boolean) => void` | Enters or leaves Select mode, where a tap selects a record rather than opening it. Leaving clears the selection. Records that aren't `selectable` never enter it. |
| `loading` | `boolean` | Whether a load is under way. |
| `error` | `boolean \| string` | Whether the load failed, or its message. |
| `onRetry` | `(() => void) \| undefined` | Loads again. |
| `timeZone` | `string` | The reader's zone in use. |
| `now` | `Date` | The moment relative dates resolve against. |
