A table of records to search, sort and page through.

## Import

```tsx
import { RecordTable, shownColumns, tableColumns, tableLayout } from '@oztix/roadie-components/record-table'
import { Records, downloadCsv, useRecords } from '@oztix/roadie-components/records'
import { recordFields, recordsToCsv } from '@oztix/roadie-core/records'
```

Fields with a `match` hold a RegExp, and columns with a `cell`, `getRowId` and the `useRecords` instance hold functions, so they can't pass from a Server Component. Build them and render the table in a client component, a file that starts with `'use client'`.

## Examples

### Default

Describe the records once as fields, pick the fields to show as columns, and pass both with the data. Search, sorting from the headers and paging come built in.

Search matches every word, in any order, in the text fields and the option labels of fields marked `searchable`. Text fields are searchable by default; other types aren't.

```tsx-live-noinline
const cities = ['Brisbane', 'Melbourne', 'Sydney', 'Perth', 'Hobart']
const names = ['Ocean Alley', 'Ball Park Music', 'Julia Jacklin', 'Angie McMahon', 'Alex Lahey', 'Middle Kids']
const shows = Array.from({ length: 240 }, (_, index) => ({
  id: `show-${index}`,
  show: `${names[index % names.length]} at Kazoo Hollow Room`,
  city: cities[index % cities.length],
  sold: (index * 37) % 2400,
  gross: (index * 7919) % 250000
}))

const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  field.text('city', { label: 'City' }),
  field.number('sold', { label: 'Sold' }),
  field.money('gross', { label: 'Gross', format: 'compactCurrency' })
]

const column = tableColumns(fields)
const columns = [
  column.field('show', { pin: true }),
  column.field('city'),
  column.field('sold'),
  column.field('gross')
]

render(
  <RecordTable
    caption='Upcoming shows'
    data={shows}
    fields={fields}
    columns={columns}
    getRowId={(row) => row.id}
  />
)
```

In TypeScript, give the builders your row type so every key is checked: `recordFields<Show>()` and `tableColumns<Show>(fields)`.

### States

Pass `loading` while records load and `error` when the load fails. With no records yet, `loading` shows still placeholder rows; with records, it dims them and runs a bar under the header. An error replaces the rows, and `onRetry` adds a Retry button. With no records, the empty state says whether none exist yet or none match, and offers to clear the search and filters.

```tsx-live-noinline
const field = recordFields()
const fields = [field.text('show', { label: 'Show' }), field.text('city', { label: 'City' }), field.number('sold', { label: 'Sold' })]

### Composition

`RecordTable` is `useRecords` and the `Records` parts put together. Build it from the parts to put controls where the screen needs them. `Records.Content` shows the view's layout, here the table from `tableLayout(columns)`.

```tsx
const layouts = [tableLayout(columns)]

function Shows() {
  const records = useRecords({ data, fields, getRowId: (row) => row.id })
  return (
    <Records records={records} layouts={layouts} caption='Upcoming shows'>
      <Records.Toolbar searchPlaceholder='Search shows' />
      <Records.Content />
      <Records.Pagination pageSizes={[20, 40]} />
      <Records.Status />
    </Records>
  )
}
```

`Records.Toolbar` holds the standard controls: the search, `Records.Options`, and with `actions`, the table actions as `Records.Actions` at the end. `searchLabel` names the search when its placeholder doesn't. Pass children to replace them, such as a `Records.Search` with your own placeholder or `aria-label` beside other controls. Keep a table's search with its table, in its toolbar, never in `Pane.Search`.

`Records.BulkActions` can sit anywhere inside the Provider: the table's `Records.Content` shows it in its header row.

### In a Pane

Most record tables live in a [`Pane`](/components/pane). Wrap the pane in `Records.Provider`, which shares the records without adding an element, and spread the parts across it:

- `Records.Toolbar` in `Pane.Body`, above the table. It sticks under the pane's header while the body scrolls, so the search stays in reach. `Pane.Header` keeps the `Pane.Title`.
- `Records.Content` in `Pane.Body`, below the toolbar. Its column headers stick under the toolbar.
- `Records.Status` anywhere inside the Provider. It renders nothing visible.
- `Records.Pagination` in `Pane.Footer`, which stays pinned at the bottom. The table's sideways scrollbar sits just above the footer.
- `Records.BulkActions` anywhere inside the Provider. The table's `Records.Content` shows it in place of the column headers while records are selected.

On a phone the table keeps its columns and scrolls sideways, with the pinned column held at the start. The second frame shows it at 390px.

### Fields and columns

A field describes one fact about a record, and its type decides how the value reads everywhere it shows:

| Field type | Reads as |
| --- | --- |
| `text` | The text. A list joins with commas. |
| `option` | Each value's label from `options`. With a `status` map, a small Badge in the key's intent. |
| `number` | Its `format`, `number` by default. Figures end-align. |
| `money` | Its `format`, `currency` by default. `currency` or `currencyKey` names a currency that isn't dollars. |
| `date` | House formats: event and access dates in the venue's zone from `timeZoneKey`, timestamps in the reader's zone, a range when the field has an `end`. |
| `boolean` | Yes or No. |

A record that holds nothing for a field shows "Not available". Text a field can't read shows as given: "To be announced" in a date field, or "On sale soon" in a number or money field, which also takes a quieter colour.

A header sorts by its field alone: words A to Z first, figures and dates largest or latest first, and a second click flips it. A field with `sortable: false` has no sort button.

A column presents one field. `tableColumns(fields).field(key, options)` takes:

- `pin` to hold the column at the start while the table scrolls sideways. The first pinned text column, or else the first text column, is the row's title, in strong text. A custom `cell` there inherits it.
- `width` as `{ min, grow }` in rem, when the content's own width doesn't suit. Without it, each column sizes from a sample of its values.
- `cell` to render the value yourself, such as an order number in `font-mono`.

The view's `layout.columns` orders and hides columns: `order` lists keys to bring forward and `hidden` lists keys to leave out. Pinned columns stay first and shown whatever the view says.

```tsx-live-noinline
const field = recordFields()
const fields = [

### Views

A view holds the search, filters, sort and layout; a position holds the page and page size. Both work uncontrolled, with `defaultView` and `defaultPosition`, or controlled, with `view` and `onViewChange`, and `position` and `onPositionChange`. A change to the search, filters or sort returns to the first page: when the page changes, `onPositionChange` hears that first, then `onViewChange` gets the view and the new position, so a parent writing both to one URL ends with the two agreeing.

Keep the view in the URL with `toSearchParams` and `fromSearchParams`, as [Records model](/foundations/records) shows. A view can name a filter on a field these records don't have, or one its field can't read, such as a date range that ends before it starts. The records skip it, show the rest, list it in `skippedFilters`, and warn in development. A sort on a field that doesn't sort is skipped too, with the same warning, and no header shows it.

```tsx-live-noinline
const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  field.text('city', { label: 'City' }),
  field.number('sold', { label: 'Sold' })
]
const column = tableColumns(fields)
const columns = [column.field('show', { pin: true }), column.field('city'), column.field('sold')]
const cities = ['Brisbane', 'Melbourne', 'Sydney', 'Perth', 'Hobart']
const shows = Array.from({ length: 40 }, (_, index) => ({
  id: `show-${index}`,
  show: `Middle Kids ${index + 1}`,
  city: cities[index % cities.length],
  sold: (index * 37) % 2400
}))

function Controlled() {
  const [view, setView] = useState({
    query: { search: 'Perth', filters: [], sort: [{ field: 'sold', direction: 'descending' }] },
    layout: { type: 'table' }
  })
  return (
    <div className='grid gap-3'>
      <p className='text-sm text-subtle'>URL: ?{toSearchParams(view).toString()}</p>
      <RecordTable
        caption='Shows'
        data={shows}
        fields={fields}
        columns={columns}
        getRowId={(row) => row.id}
        view={view}
        onViewChange={setView}
      />
    </div>
  )
}

render(<Controlled />)
```

### Options

`Records.Options` is the Configure button in the toolbar, after the search and before any table actions, so their More actions menu stays last. It opens a popover below the button, lined up with its end, or a bottom drawer on a phone, and every change applies at once.

- **Sort** lists each level the view sorts by: a field, then its direction in the field's own terms, such as A to Z, Low to high or Earliest first. Add sort starts with the first sortable field, its natural way, and Add another sort breaks ties with a field not sorted yet. A header click still sorts by that column alone. A level on a field that doesn't sort isn't listed, and changes here leave it in the view. A level that repeats a field sorts nothing, so changes here drop it.
- **Columns** lists the table's columns in their order. Drag a handle to move a column, or click it, or press Enter on it, for a Move menu. The eye beside each column shows or hides it, and a hidden column stays in the list, dimmed, in its place. Pinned columns always come first and always show, so the list names them rather than offering them. The last shown column can't be hidden. The table loads this list once the page is idle, or as a pointer or focus reaches the button, so drag and drop stays out of the table's first load and the first open doesn't wait for it.

The options write the view, like the headers do: the sort to `query.sort`, and the columns to `layout.columns`, with the whole `order` once a column moves and the `hidden` keys. Put back the way the columns are defined, the layout leaves both out, so `equalViews` reads it as unchanged. A view's keys for columns this table doesn't have, such as one only some people see, are kept. The button shows only when a field sorts or a column can move or hide: two columns that aren't pinned, or one beside a pinned column.

```tsx-live-noinline

A layout adds its own settings under the sort with a `Settings` component in its definition, as `tableLayout` does for the columns. A lazy one can carry a `preload` function, which `Records.Options` calls once the page is idle or its button is reached.

### Selection and actions

`bulkActions` turns on a checkbox for each record and shows the bulk actions once something is selected. An action gets the selection and the query it was taken against: the picked ids, or every matching record but some. It never gets a record the search and filters hide. Selection is session state, like the page, and works controlled with `selection` and `onSelectionChange` or uncontrolled with `defaultSelection`. A search or filter change drops picked records it hides, and drops a "select all".

`rowActions` returns menu items for a record, shown in a menu on its row named "More actions for" the record. `getRowHref` links each record to its page through the title column. When records can be selected, clicking anywhere else on a row selects it, and Shift extends the selection from the last one picked; otherwise the click follows the link. Cmd or Ctrl opens the record in a new tab. Return `undefined` for a record with no page.

While records are selected, the bulk actions take the column headers' place in the same sticky row, so the rows never move and the bar stays in view as the table scrolls down or sideways. The page checkbox stays at the start. The count, such as "3 selected", opens a menu with Clear selection, and with "Select all" once the whole page is checked and more records match. Actions follow as buttons, and those that don't fit move into a More actions menu at the end. The headers come back once the selection clears. Danger actions ask first unless `confirm` is `false`, and any other action asks when given `confirm`.

### Table actions and export

`tableActions` act on everything the search and filters match, with nothing selected, such as exporting an attendee list. Each gets the applied query and the records. The first shows as a button at the end of the toolbar and the rest sit in a "More actions" menu after it. In a toolbar under 40rem they all sit in the menu. Danger actions confirm first, as bulk actions do. They stay in the toolbar while records are selected, apart from the bulk actions in the header row, so it stays clear which actions use the selection.

`recordsToCsv(rows, fields, { timeZone })` from `@oztix/roadie-core/records` writes rows as CSV, one column per field, each value as the table shows it, and `downloadCsv` saves it. In the browser, `records.matchingRows` holds every matching record in the current sort, across pages, and `shownColumns(columns, records.view.layout)` gives the columns the table shows, in its order. Pass `{ values: 'raw' }` to write plain numbers a spreadsheet can sum. Text that starts like a formula, such as `=` or `@`, is written with a leading apostrophe so a spreadsheet shows it rather than runs it. A column with its own `cell` exports its field's value, not what your cell draws.

```tsx-live-noinline
const names = ['Mia Tran', 'Jack Ellis', 'Ava Nguyen']
const tickets = [
  { value: 'ga', label: 'General admission' },
  { value: 'vip', label: 'VIP' },
  { value: 'early', label: 'Early bird' }
]
const attendees = Array.from({ length: 60 }, (_, index) => ({
  id: `attendee-${index}`,
  name: `${names[index % names.length]} ${Math.floor(index / names.length) + 1}`,
  ticket: tickets[index % tickets.length].value,
  order: `OZ-${48210 + index * 7}`,
  paid: [79.9, 149, 59][index % tickets.length]
}))

const field = recordFields()
const fields = [
  field.text('name', { label: 'Name' }),
  field.option('ticket', { label: 'Ticket type', options: tickets }),
  field.text('order', { label: 'Order' }),
  field.money('paid', { label: 'Paid' })
]
const column = tableColumns(fields)
const columns = fields.map((field, index) => column.field(field.key, { pin: index === 0 }))
const exportCsv = (records) =>
  downloadCsv(
    recordsToCsv(
      records.matchingRows.map(({ row }) => row),
      shownColumns(columns, records.view.layout).map(({ field }) => field),
      { timeZone: records.timeZone }
    ),
    'attendees.csv'
  )

render(
  <RecordTable
    caption='Attendees'
    data={attendees}
    fields={fields}
    columns={columns}
    getRowId={(row) => row.id}
    recordName={{ one: 'attendee', other: 'attendees' }}
    tableActions={[
      {
        label: 'Export CSV',

### Server data

Pass `rowCount` and the records stop searching, filtering, sorting and paging in the browser. `data` is one page, in the order the server returned it, and `rowCount` counts every record that matches. Hold the view and position yourself, usually in the URL, and fetch whenever either changes, or the viewer's zone does: relative dates such as "today" resolve in it, and a server render reads UTC until the page hydrates. The search waits for a 250ms pause in typing before `onViewChange` hears it, so a request doesn't leave on every keystroke. Clearing it is immediate.

Set `loading` from whether the rows for the current view and position have arrived, so it is already true in the render where either changes. While `loading` or `error` is set, the records keep a page past the old count, so a linked page waits for the new count before it moves, and `Records.Status` waits for the new count before it announces it. Once given, `rowCount` keeps server mode on: left `undefined` while a page loads, it keeps the last count. Pass 0 until the first count arrives. Take each change `onViewChange` reports: a parent that ignores a search leaves the field showing it. Column widths come from the first page a search or filter brings, and hold as people page, so the columns don't shift.

Selection works against the total. Records ticked on different pages stay selected, and Select all picks `{ allMatching: true, except }`, counted from `rowCount`. A bulk action gets that selection and the query it was taken against, so the server acts on the same records. A new search or filter clears the selection, since only the server knows what still matches; a new sort or page keeps it. Selecting needs `getRowId`, as index ids repeat on every page. `matchingRows` holds only the page, so export on the server, as Table actions shows.

This example's server is pretend: it filters and sorts with core's `resolveRecordQuery`, `compileRecordQuery` and `sortRecords`, as an index would, waits half a second, and shows the Meilisearch search it stands in for.

```tsx-live-noinline

const cities = ['Brisbane', 'Melbourne', 'Sydney', 'Perth', 'Hobart']
const everyShow = Array.from({ length: 400 }, (_, index) => ({
  id: `show-${index}`,
  show: `${names[index % names.length]} ${Math.floor(index / names.length) + 1}`,
  venue: venues[index % venues.length],
  city: cities[index % cities.length],
  status: ['on_sale', 'on_sale', 'sold_out', 'cancelled'][index % 4],
  sold: (index * 37) % 2400
}))

const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  field.text('venue', { label: 'Venue' }),
  field.text('city', { label: 'City' }),
  field.option('status', {
    label: 'Status',
    status: {
      on_sale: { intent: 'success', label: 'On sale' },
      sold_out: { intent: 'neutral', label: 'Sold out' },
      cancelled: { intent: 'danger', label: 'Cancelled' }
    }
  }),
  field.number('sold', { label: 'Sold' })
]
const column = tableColumns(fields)
const columns = fields.map((field, index) => column.field(field.key, { pin: index === 0 }))
const timeZone = 'Australia/Sydney'

function pretendServer(view, position) {
  const now = new Date()
  const query = resolveRecordQuery(view.query, fields, { now, timeZone })
  const matching = sortRecords(everyShow.filter(compileRecordQuery(query, fields)), query.sort, fields, { timeZone })
  const start = position.page * position.pageSize
  return new Promise((resolve) =>
    setTimeout(
      () =>
        resolve({
          rows: matching.slice(start, start + position.pageSize),
          rowCount: matching.length,
          search: toMeilisearch(view, fields, { now, timeZone, position })
        }),
      500
    )
  )
}

const firstView = { query: { search: '', filters: [], sort: [] }, layout: { type: 'table' } }

function ServerShows() {

  const [position, setPosition] = useState({ page: 0, pageSize: 25, row: 0 })

  useEffect(() => {
    let current = true

      if (current) setResult({ ...next, key })

      current = false
    }
  }, [key])

  return (
    <div className='grid gap-3'>

        caption='Shows'

        rowCount={result.rowCount}

        columns={columns}
        getRowId={(row) => row.id}
        recordName={{ one: 'show', other: 'shows' }}
        view={view}
        onViewChange={setView}
        position={position}
        onPositionChange={setPosition}
        bulkActions={[{ label: 'Export', onAction: (selection, query) => console.log('export', selection, query) }]}
      />
      {result.search && (
        <pre className='rounded-md bg-sunken p-3 font-mono text-xs break-all whitespace-pre-wrap text-subtle'>

        </pre>

render(<ServerShows />)
```

With Meilisearch, `toMeilisearch(view, fields, { now, timeZone, position })` from `@oztix/roadie-core/records/meilisearch` turns the view and position into a search. It adds `page` and `hitsPerPage`, so the response's `totalHits` counts the matches for `rowCount`. Meilisearch stops counting at the index's `pagination.maxTotalHits`, 1,000 by default, so raise it to the most records a screen can match. Pass the viewer's zone, `records.timeZone`, so "today" means their day. [Records model](/foundations/records) lists the index shape it needs.

```tsx
const { q, ...params } = toMeilisearch(view, fields, {
  now: new Date(),
  timeZone,
  position
})
const response = await client.index('events').search(q, params)
const page = { rows: response.hits, rowCount: response.totalHits }
```

The example fetches `view`, which only the table changes. A view from a URL read with `fromSearchParams`, or checked with `validateRecordView`, is safe to fetch too. Built from `useRecords`, fetch `records.appliedView.query` instead: it leaves out the filters and sorts the fields can't apply, as the table does.

### Range loading

Pass `loadRange` for one long list with no pages that loads the records on screen as people scroll. The list asks for the rows on screen plus a screen either side, a page per request, as `{ start, end }` with `end` exclusive. Each range is one whole page, page `start / pageSize`, so fetch `pageSize` records from `start`; the last one can run past the end of the list. Fetch it, put the records in `data` at their index with `placeRange` from `@oztix/roadie-core/records`, then resolve. Rows that haven't arrived show as grey placeholders. Pass `rowCount` as the total that matches, so the scrollbar is the right length from the first frame. A count that grows, as when a record is added at the end, loads the rows it adds. A record added anywhere else moves the rows after it, so clear `data` then.

The server searches, filters and sorts, as in server mode, and the search waits for a pause in typing. Clear `data` when the query or the zone changes, or the old records count as loaded and are never fetched again. This example keeps the records with the query they belong to, drops a response for an older one, and keeps the last total until the new query's first response, so the scrollbar holds its length. Every request waits 400ms.

If `loadRange` rejects, the range shows an error row in place of its records, with Retry, and the records already loaded stay. When nothing has loaded yet, the table shows its error state instead. Range mode stops at 300,000 rows. With range loading, `Records.Pagination` shows the count instead of pages, such as "1,284 shows", or "50+ shows" while the total is unknown, with no page buttons and no rows per page: the list scrolls. Paging stays for paged tables.

Use range loading for long lists people scroll, open a record and come back to. Use pages when people jump to a known page, or the list is short.

```tsx-live-noinline
const names = ['Ochre Kite Weekender', 'Lampshade Disco', 'Raffia Spaceship', 'Nectarine Hoedown', 'Tuxedo Possum Cabaret', 'Marzipan Thunderclap']
const cities = ['Brisbane', 'Melbourne', 'Sydney', 'Perth', 'Hobart']
const everyShow = Array.from({ length: 5000 }, (_, index) => ({
  id: `show-${index}`,

  city: cities[index % cities.length],
  sold: (index * 37) % 2400
}))

const field = recordFields()
const fields = [
  field.text('show', { label: 'Show' }),
  field.text('city', { label: 'City' }),
  field.number('sold', { label: 'Sold' })
]

    setTimeout(

        resolve({
          rows: matching.slice(start, end),

const firstView = { query: { search: '', filters: [], sort: [] }, layout: { type: 'table' } }

function RangeShows() {
  const [view, setView] = useState(firstView)

    <div className='grid gap-3'>
      <RecordTable
        caption='Shows'
        data={result.data}
        rowCount={result.rowCount}
        fields={fields}
        columns={columns}
        getRowId={(row) => row.id}
        recordName={{ one: 'show', other: 'shows' }}

        onViewChange={setView}
        defaultPosition={{ pageSize }}
        timeZone={timeZone}
        loadRange={async (range) => {

        <pre className='rounded-md bg-sunken p-3 font-mono text-xs break-all whitespace-pre-wrap text-subtle'>

        </pre>
      )}
    </div>
  )

render(<RangeShows />)

With Meilisearch, fetch each range as a page: `toMeilisearch(view, fields, { now, timeZone, position: { page: start / pageSize, pageSize } })`, and pass `totalHits` as `rowCount`. Raise the index's `pagination.maxTotalHits` to the longest list a screen can show.

Some APIs page with a cursor and never say how many records match. Leave out `rowCount` and the list asks for one range at a time, from the end of what it holds, and stops once a range comes back short or resolves without placing any records. The scrollbar grows as records arrive. Keep each range's cursor by where it starts, and set the page size to the API's.

The list reports the first row on screen as `position.row`, through `onPositionChange`, a few times a second while people scroll. Keep it with the view, such as in the URL, and coming back to the list lands on the same row, loading its range first. A row the list reported itself never scrolls it back, so a slow router replaying an older row can't jump the list. Scrolling changes `row` often, so write it to the URL without adding history.

### Long lists

By default the page, or the pane, scrolls the rows down, and the table scrolls sideways on its own with a Roadie scrollbar that sticks to the bottom of whatever scrolls the page. Past 100 rows, only the rows near the screen render, so a long page scrolls smoothly. Find in page and printing then see only those rows, so keep pages to 100 where people search the page or print it. If the focused row scrolls away, focus moves to the table, keeping the reader's place. Give `Records.Content` (or `RecordTable`) a `maxHeight` to scroll the rows both ways in a box of their own, with the header and the pinned column held in place. `fill` does the same at its parent's height, such as a `Pane.Body`.

## Accessibility

- `caption` names the table. Every part reads as a table, with column headers and cells.
- A sortable column's header is a button. The sorted column carries `aria-sort`.
- When the table scrolls sideways, its frame is a region named "Shows, scrolls sideways" for a caption of Shows, and the scroller is its one tab stop, so keyboard users can scroll it with the arrow keys. In its own box (`maxHeight` or `fill`), the box is the region, named "Shows, scrolls".
- `Records.Status` is a live region. It announces Loading, the error, and the result count while a search or filter narrows the list.
- When the table holds only some of its rows (a page of several, more than 100 rows, or a list loaded by range), it carries `aria-rowcount`, counting every match (up to 300,000 loading by range) and the header row, and each row its `aria-rowindex`, so screen readers announce "row 52 of 121". Loading by range, the count is `-1` until the total is known.
- Loading by range, the table is `aria-busy` while a range loads, placeholders are hidden from screen readers, and a failed range is announced, such as "Couldn't load more shows". The result count is announced only once the total is known. The header checkbox is named "Select loaded rows".
- State titles are paragraphs, not headings, since the table can't know the page's outline. Their icon tiles are hidden from screen readers.
- Escape clears the search. The clear button keeps focus in the search field. Give `Records.Search` an `aria-label` when its placeholder doesn't name it well enough.
- Each record's checkbox is named "Select" followed by the record's title, or its id with no title, and the header checkbox is named "Select page", with a mixed state when only some of the page is checked.
- `Records.Status` also announces the selection, such as "3 selected, 24 results". It announces a search's count once typing settles, not on every keystroke, and against a server once the new count loads.
- While records are selected, the bulk actions are a toolbar named "Bulk actions" in the header row, beside "Select page", which keeps focus as the bar replaces the column headers. The headers stay in the table for screen readers, and the toolbar sits in a last header with no cells under it. Arrow keys move between its controls. Escape clears the selection and returns focus to "Select page".
- Each row's actions menu is named "More actions for" the record's title. Table actions past the first sit behind a button named "More actions". A running action's control stays focusable but disabled, with `aria-busy`. A confirmation is an alert dialog.
- The Configure button is named "Configure table", as is the dialog it opens. Its sort controls are named "Sort by", then "Then by, level 2" and so on, and for each level the field's order, such as "Sold order". Adding a level moves focus to its field, and removing one moves focus to the Remove of the level that takes its place, or of the one before it, or to Add sort. Each column's handle is named "Reorder" and the column, its eye is a toggle button named "Show" and the column, pressed while the column shows (the last shown column's is disabled and says why), and each move is announced, such as "Gross moved to position 1 of 4 columns".
- A row with `getRowHref` holds a real link: it opens in a new tab with Cmd or Ctrl, and works with every other link convention, not just a click handler.

## Hooks

### useRecords

```tsx
function useRecords<Row extends object>(options: UseRecordsOptions<Row>): RecordsInstance<Row>
```

Holds the view, position and selection, and searches, filters, sorts and pages the records in the browser, or with `rowCount` leaves that to a server. Takes `data`, `rowCount`, `fields`, `getRowId`, `view`, `defaultView`, `onViewChange`, `position`, `defaultPosition`, `onPositionChange`, `selectable`, `selection`, `defaultSelection`, `onSelectionChange`, `rowActions`, `getRowHref`, `recordName`, `loading`, `error`, `onRetry`, `timeZone` (the reader's, which decides what "today" is), `now` (when relative dates resolve, by default when the list mounted) and `loadRange` (which loads the list by range as people scroll). Pass the result to `Records` or `Records.Provider`.

| Field | Type | Description |
| --- | --- | --- |
| `mode` | `'browser' \| 'server' \| 'range'` | Where the records are searched and paged: `server` once `rowCount` is given, `range` once `loadRange` is. |
| `data` | `readonly Row[]` | Every record held, before search, filters and paging. In server mode, the page; in range mode, the records loaded, in order. |
| `fields` | `readonly RecordField[]` | What each record holds. |
| `view` | `RecordView` | The search, filters, sort and layout. |
| `appliedView` | `RecordView` | The view the rows show, and the one to fetch in server mode, without the filters and sorts the fields can't apply. In the browser its search lags typing while a long list filters. Its `query` keeps its identity while its content holds. Key a fetch on it, the position and `timeZone`. |
| `searchText` | `string` | What the search field shows. In server mode it runs ahead of the view's search until typing pauses. |
| `resolvedQuery` | `ResolvedRecordQuery` | The applied query, with relative dates fixed and unusable filters skipped. |
| `rows` | `readonly { id: string; row: Row }[]` | The current page. In range mode, every record loaded. |
| `resultCount` | `number` | Records the search and filters match: `rowCount` in server mode. |
| `filtered` | `boolean` | Whether a search or filter narrows the records. |
| `position` | `{ page: number; pageSize: number; row: number }` | The page, zero-based, and its size. In range mode, `row` is the first row on screen and each range is one page. |
| `pageCount` | `number` | Pages at this size, at least one. |
| `setView` | `(view: RecordView) => void` | Replaces the view. |
| `skippedFilters` | `readonly number[]` | Filters in the view, by index, that these fields can't apply. |
| `setSearch` | `(search: string) => void` | Sets the search and returns to the first page. In server mode, once typing pauses for 250ms, or at once when cleared. |
| `addFilter` | `(filter: RecordFilter) => void` | Adds a filter. |
| `updateFilter` | `(index: number, filter: RecordFilter) => void` | Replaces the filter at an index. |
| `removeFilter` | `(index: number) => void` | Removes the filter at an index. |
| `clearQuery` | `() => void` | Clears the search and filters, keeping the sort and layout. |
