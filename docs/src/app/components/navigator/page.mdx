A full-height application frame — vertical navigation on desktop, a tab
bar on mobile — that adapts to whether the product has nested sections.

## Import

```tsx
import { Navigator } from '@oztix/roadie-components/navigator'
```

## Anatomy

Navigator owns the whole viewport (`100dvh`). `Navigator.Primary` is the
primary navigation: vertical on desktop and a floating horizontal tab bar
on phones — both are derived from the same `Navigator.Item` children, so
you author the destinations once. `Navigator.Content` arranges one or more
[`Pane`](/components/pane)s, each of which owns its own scroll.

Two slots mark position rather than declaring destinations.
`Navigator.Brand` pins a logo or wordmark to the top of the primary navigation, and
`Navigator.End` anchors a group — account, settings — to the bottom.
Both are found by reference and skipped in the item walk, so neither
counts toward the navigation's form or nesting. `Navigator.Brand` is desktop-only:
the tab bar has no brand slot, so it renders nothing below `md`. Give it
a mark that survives the compact form — it centres its contents
and hides anything you mark
`group-data-[form=compact]/primary:hidden`.

Navigator is always **controlled** — the active `value` belongs to your
router. The examples below hold it in `useState` to stay
self-contained; in a real app you would derive `value` from the URL and
let each item's `href` drive navigation.

Every example is wrapped in a fixed-height, `overflow-hidden` box so the
frame renders whole inside the page. The floating tab bar and the
overflow fold are the **mobile** presentation — narrow your viewport (or
open the example on a phone) to see them; a wide viewport shows the
vertical navigation.

**Keep the whole tree in a client component.** `Navigator.Primary`,
`Navigator.Secondary`, `Navigator.Group` and `Navigator.Panel` all find
something by element reference — items, a group's title, a panel's own
props — rather than by walking rendered output. React Flight replaces the
type of every element authored in a server component with a lazy wrapper,
so a server-authored tree silently renders the wrong navigation form, drops
group titles, and produces an empty tab bar. Author the whole Navigator
inside a `'use client'` component — `Navigator.Content` and `Pane` are the
only pieces that are server-safe on their own. See
`docs/contributing/COMPOUND_PATTERNS.md` §1.2.

### Grouping

`Navigator.Group` heads a run of `Navigator.Item`s with a `Navigator.GroupTitle`
— its first child. The title renders as an `<h2>` by default; pass `render` to
change the level when the page's own outline needs it. The group announces to
assistive tech as a named list, via `aria-labelledby` on the run's `<ul>`, so
screen reader users hear "Manage, list, 2 items" rather than an unlabelled run.

Groups flatten where there's no room for a heading: on the mobile strip and in
the tab bar's first four slots, the items render inline in author order and
the title is dropped — the destinations are still reachable, just without the
grouping. Items that fold into the More pane keep their group there, as a
titled `List.Group`, and `Navigator.End` items follow as a section of their
own.

### Overflow

The mobile tab bar holds at most five slots. With six primary items plus a
`Navigator.End`, the tail folds into a final **More** tab. Opening it pushes a
full-screen `Navigator.Overflow` pane onto the stack — the tab bar stays
visible, because you're still inside the nav, not away from it — and the
indicator slides to the More tab to mark it selected. It closes by tapping a
row, tapping More again, or pressing Escape; there is no outside-tap, because
there is no floating surface to tap outside of.

Declaring `Navigator.Overflow` yourself — with a `Pane.Header` for a title —
is the composable form, and the one on this page. Omit it and
`Navigator.Content` generates one titled "More", with a `Pane.Header` and
`Navigator.OverflowItems` beneath it. The vertical navigation always shows every item — narrow your
viewport to see the fold.

### Tab slots

`Navigator.Primary`'s `tabs` prop picks which items take the tab bar's slots,
in tab order — independent of source order. Omit it and the bar uses source
order, folding the tail past four into More, which is what every example
above does. `tabs` is a tuple type capped at four values, because the fifth
slot is always More; TypeScript rejects a fifth.

Declaring `tabs` declares the whole membership: any item not named in the
array folds into the overflow, even if it would otherwise have fit — a lone
unnamed item still discloses rather than getting its own tab. A value in
`tabs` that doesn't match any `Navigator.Item`'s `value` is a dev-mode
warning, and that slot is dropped.

```tsx-live-noinline
function TabSlotsNav() {
  const [active, setActive] = useState('/')
  const labels = {
    '/': 'Home',
    '/listings': 'Listings',

  return (
    <div className='h-[30rem] overflow-hidden rounded-2xl border border-subtle'>
      <Navigator value={active} onValueChange={setActive} className='h-full'>
        <Navigator.Primary
          aria-label='Main'
          tabs={['/', '/calendar', '/listings', '/messages']}
        >
          <Navigator.Item value='/' icon={<MagnifyingGlassIcon />}>
            Home
          </Navigator.Item>
          <Navigator.Item value='/listings' icon={<TicketIcon />}>
            Listings
          </Navigator.Item>
          <Navigator.Item value='/calendar' icon={<StarIcon />}>
            Calendar
          </Navigator.Item>

    </div>
  )
}
render(<TabSlotsNav />)
```

### Panel

`Navigator.Panel` gives an item a menu instead of a destination — an account
switcher, a settings menu. Declaring one makes the item a **disclosure**: any
`href` on it is ignored, exactly as a `Navigator.Secondary` makes it a
section. It works on any item, primary or `Navigator.End`.

One declaration, two presentations, neither configurable: a popover anchored
to the item's row from `md`, and below it the item's own tab in the bar toggles
a full-screen pane — the same tab, not a separate overlay. Put the panel's
`List` at its own top level — below `md` it renders inside the pane, whose
list unwind reaches direct children only.

```tsx-live-noinline
function PanelNav() {
```

### Pane header

[`Pane.Header`](/components/pane) is sticky chrome at the top of a pane: a
`Pane.Title`, a back affordance (top-left, from `backHref` or `onBack`), and a
`Pane.Actions` slot (top-right). Body content scrolls beneath it. Here a `list`
pane drills into a `detail` pane — selecting a row reveals the detail, and the
back control clears the selection. It is depth-aware: a `list` (first) pane has
nothing to go back to and shows none, and the back row hides from `lg` up, where
every pane is a column beside its siblings rather than stacked over them.

The header is also where Navigator renders the active section's secondary nav on
mobile. Only the **top** pane's header draws it, so a stack of mounted panes can
never produce two section-nav landmarks.


## Long sections

`Navigator.Secondary` is right for a handful of flat sub-pages. Once a section's
list is long enough to scroll on its own, needs grouping, needs filtering, or its
rows carry more than a label, it wants a column rather than a nested run of
rows — so declare a [`Pane`](/components/pane) of your own inside
`Navigator.Content` and leave the section without a `Navigator.Secondary`.

<Guideline title='Choosing Secondary vs. a Pane'>
  <Guideline.Do code={`<Navigator.Item value='/events' href='/events'>\n  Events\n  <Navigator.Secondary aria-label='Events pages'>\n    <Navigator.Item value='/events/upcoming' href='/events/upcoming'>Upcoming</Navigator.Item>\n    <Navigator.Item value='/events/past' href='/events/past'>Past</Navigator.Item>\n  </Navigator.Secondary>\n</Navigator.Item>`}>
    **Secondary** for a handful of flat sub-pages with short labels. It
    keeps the section's structure visible next to its siblings and costs
    no layout.
  </Guideline.Do>
  <Guideline.Dont code={`<Navigator.Secondary aria-label='Catalogue sections'>\n  <Navigator.Item value='/catalogue/tshirts'>T-shirts</Navigator.Item>\n  ... 40 more rows ...\n</Navigator.Secondary>`}>
    Forty rows in the primary navigation is not a nested section, it is a list. Give it
    a `Pane` with a `List` inside instead — it costs a column, so it suits
    a section a user dwells in rather than passes through.
  </Guideline.Dont>
</Guideline>

Rough dividing line: under ~10 flat items, `Navigator.Secondary`. Grouped,
filterable, or thumbnail-bearing, a `Pane`. A heuristic, not a rule.

A section with no `Navigator.Secondary` still lights up on its sub-pages: a
section's `value` is matched as a **route prefix**, so any destination whose
value starts with `${value}/` keeps the section branch-active in both
orientations. `Navigator.Primary` passes that branch-active state straight
through as the tab's `aria-current='page'`, so the section tab announces
itself as the current page too, alongside whatever destination is actually
selected inside it — a recorded, accepted imprecision rather than a
guarantee. The tab bar has no control pointing at a sub-page it never
rendered, so the nearest reachable ancestor claims the page role instead of
leaving it unclaimed.

Filtering the list is the consumer's own `.filter()` over its own data, before
it renders the rows — Navigator has no filter registry, and a `Pane` is just a
scroll container.

## Pane surfaces and the mobile stack

Both belong to [`Pane`](/components/pane) rather than to Navigator, so they are
documented there. The two facts worth knowing from here:

- **Below `lg` panes stack**, full-bleed, one visible at a time, and push/pop
  between them animates. Which pane is on top is derived from the deepest pane
  marked `current` — declare it, and the arrangement follows.
- **`Navigator.Content` is the orchestrator.** Panes announce themselves to
  the nearest `Navigator.Content` through context, wherever they sit in its
  subtree — a pane returned by a route, a Next.js parallel-route slot, or a
  wrapper component all participate normally. What still breaks is having no
  `Pane` reachable at all: nothing registers, so stack position, push/pop
  motion and `primaryNav` all stay inert, and `Navigator.Content` warns to
  the console about it in development.

## Guidelines

- **Drive selection from the router.** Navigator is controlled. Derive
  `value` from the URL and give each item an `href` so back/forward and
  deep links work; reach for `onValueChange` only when there is no route
  to own the state.
- **Use `Navigator.End` for account and settings**, not another primary
  item — it anchors to the bottom of the primary navigation and becomes the final
  mobile tab.
- **Let the top pane declare what the mobile bar does.** `Pane`'s `primaryNav`
  is `auto` by default: the bar collapses to the active tab as the pane
  scrolls and returns at the top. `visible` pins it, `hidden` takes it away
  for the pushed screen (iOS's `hidesBottomBarWhenPushed`).
- **Panes scroll through a `ScrollArea` viewport.** `Pane` renders a
  [`ScrollArea`](/components/scroll-area) whose viewport
  (`[data-slot="pane-viewport"]`) is the real scroll container — anything
  reading `scrollTop` or calling `scrollTo` on a pane must target the
  viewport, not the `<section>`.
- **Sections remember where you left them.** Returning to a section you have
  visited before lands you back where you left it, not at its declared
  landing. That memory lives only in the running app — the URL is the only
  source of truth, so a reload always starts every section at its declared
  `href`.

## Accessibility

- **Landmarks**: the vertical navigation, the mobile tab bar, and each declared
  secondary render as distinct `<nav>` elements. `aria-label` on
  `Navigator.Primary` and `Navigator.Secondary` is **required** so screen
  readers can tell them apart.
- **Current destination**: the active item carries `aria-current='page'`.
- **Collapsed tabs stay in the accessibility tree** — they shrink to zero
  width rather than `display:none`, so the full destination set remains
  reachable.
