A full-height application frame — floating capsules in a vertical navigation
on large screens, a floating tab bar on phones — with one navigation model at
every size.

## Import

```tsx
import {
  Navigator,
  useNavigatorSection
} from '@oztix/roadie-components/navigator'
```

## Anatomy

Navigator owns the whole viewport (`100dvh`). `Navigator.Primary` is the
primary navigation, authored once and drawn in two orientations: a vertical
navigation from `md`, where each group is a floating capsule of icon tiles, and
a floating horizontal tab bar on phones. `Navigator.Content` arranges one or
more [`Pane`](/components/pane)s, each of which owns its own scroll.

```tsx
<Navigator value={path} expanded={open} onExpandedChange={setOpen}>
  <Navigator.Primary aria-label='Documentation'>
    <Navigator.Brand />
    <Navigator.ExpandToggle />
    <Navigator.Group visibilityPriority='high'>
      <Navigator.GroupTitle>Docs</Navigator.GroupTitle>
      <Navigator.Item value='/' href='/' icon={<HouseIcon />}>
        Home
        <Navigator.Secondary aria-label='Home pages' root='page'>…</Navigator.Secondary>
      </Navigator.Item>
      <Navigator.Item value='/components' href='/components' icon={<CubeIcon />}>
        Components
        <Navigator.Secondary aria-label='Components' searchable>…</Navigator.Secondary>
      </Navigator.Item>
    </Navigator.Group>
    <Navigator.Item
      value='account'
      icon={<UserIcon />}
      placement='pinned'
      badge={<Badge intent='danger' emphasis='strong'>3</Badge>}
    >
      Account
      <Navigator.Menu>…</Navigator.Menu>
    </Navigator.Item>
  </Navigator.Primary>
  <Navigator.Content>
    <Pane role='detail' current>…</Pane>
  </Navigator.Content>
</Navigator>
```

The vertical navigation has three regions, top to bottom: `Navigator.Brand` with
the expand toggle, the cluster of capsules, and the pinned items. Each
`Navigator.Group` is a capsule;
consecutive loose items share one. Collapsed, the cluster centres between brand
and pinned and shows icon tiles labelled by a tooltip. Expanded, it stays
centred and shows labels beside the icons; only when it outgrows the space does
it top-align and scroll on its own.

`Navigator.Brand` is large-screen only — the tab bar has no brand slot. Every
Navigator has one, and in development `Navigator.Primary` warns without it. It
links home: `href` defaults to `'/'` and routes through `RoadieLinkProvider`
like every Navigator destination; pass `href` to point it elsewhere.

With no children it renders the Oztix [`Logo`](/components/logo), which names
the link "Oztix". Collapsed, only the mark shows; expanded, the wordmark opens
beside it with the labels. A `Logo` with a `product` opens its product name the
same way.

Your own brand goes in as children. Its content names the link, so label the
mark (`alt`, or `role='img'` with an `aria-label`) and hide a wordmark that
repeats it with `aria-hidden`. The mark, its first child, sits on the icon
column in both states, so it never moves; anything after it fades in once
expanded. Hide a wordmark until then with `hidden navigator-expanded:inline`.

```tsx
<Navigator.Brand />

<Navigator.Brand>
  <Logo product='Studio' />
</Navigator.Brand>

<Navigator.Brand>
  <img src='/mark.svg' alt='Acme' className='size-8' />
  <span aria-hidden className='hidden navigator-expanded:inline'>Acme</span>
</Navigator.Brand>
```

Navigator is always **controlled** — the active `value` belongs to your
router. The examples below hold it in `useState` to stay self-contained. The
ones with routes use `DemoRouter` instead, a docs-only stand-in for your router
that holds the path and whose links change it rather than the URL.

Every example is wrapped in a fixed-height, `overflow-hidden` box so the
frame renders whole inside the page. Narrow your viewport, or open the page on a
phone, to see the tab bar and the stacked panes.

**Keep the whole tree in a client component.** `Navigator.Primary`,
`Navigator.Secondary`, `Navigator.Group`, `Navigator.Menu` and
`Navigator.ExpandToggle` are all found by element reference — items, a group's
title, a menu's rows — rather than by walking rendered output. React Flight
replaces the type of every element authored in a server component with a lazy
wrapper, so a server-authored tree silently loses its items, group titles and
menus. The same walk means items must be direct children of `Primary`, a
`Group` or a `Secondary` (mapped arrays are fine); an item inside a Fragment or
your own wrapper component is skipped. Author the whole Navigator inside a
`'use client'` component — `Navigator.Content` and `Pane` are the only pieces
that are server-safe on their own. See `docs/contributing/COMPOUND_PATTERNS.md`
§1.2.

### Showing the list from the URL

Roadie never reads the URL. To let a phone user see the list over a sub-page
without leaving it, derive `showList` from a query parameter and turn
`onShowListChange` into a URL update — the docs use `?nav`. With it wired,
tapping the active section's tab shows the list instead of going to the section
route. Here `useState` stands in for the query string; navigating clears it,
as a new URL would. Narrow your viewport and tap Events on a sub-page.

```tsx-live-noinline
function ListFromUrlNav() {
  const [showList, setShowList] = useState(false)
  return (
    <div className='h-[30rem] overflow-hidden rounded-2xl border border-subtle'>
      <DemoRouter
        initialPath='/events/upcoming'
        onNavigate={() => setShowList(false)}
      >
        {(path) => (
          <Navigator
            value={path}
            showList={showList}
            onShowListChange={setShowList}
            className='h-full'
          >
            <Navigator.Primary aria-label='Organiser'>
              <Navigator.Brand href='/events' />
              <Navigator.Item value='/events' href='/events' icon={<TicketIcon />}>
                Events
                <Navigator.Secondary aria-label='Events pages'>
                  <Navigator.Item value='/events/upcoming' href='/events/upcoming'>
                    Upcoming
                  </Navigator.Item>
                  <Navigator.Item value='/events/past' href='/events/past'>
                    Past
                  </Navigator.Item>
                </Navigator.Secondary>
              </Navigator.Item>
              <Navigator.Item value='/marketing' href='/marketing' icon={<EnvelopeIcon />}>
                Marketing
              </Navigator.Item>
            </Navigator.Primary>
            <Navigator.Content>
              <Pane role='detail' current>
                <Pane.Header>
                  <Pane.Title>{path}</Pane.Title>
                </Pane.Header>
                <p className='px-4 pb-4 text-subtle'>
                  {showList ? 'The list is showing (?nav).' : 'No ?nav in the URL.'}
                </p>
              </Pane>
            </Navigator.Content>
          </Navigator>
        )}
      </DemoRouter>
    </div>
  )
}
render(<ListFromUrlNav />)
```

In Next.js, read the parameter in a leaf inside its own `Suspense` boundary —
`useSearchParams` client-renders a prerendered page up to the nearest one — and
push rather than replace, so the browser's Back undoes "show the list".

```tsx
'use client'

import { Suspense, useCallback, useEffect, useState } from 'react'

import { usePathname, useRouter, useSearchParams } from 'next/navigation'

import { Navigator } from '@oztix/roadie-components/navigator'

const NAV_LIST_PARAM = 'nav'

function NavListQuery({ onChange }: { onChange: (next: boolean) => void }) {
  const showList = useSearchParams().has(NAV_LIST_PARAM)
  useEffect(() => {
    onChange(showList)
  }, [showList, onChange])
  return null
}

export function AppNavigator() {
  const pathname = usePathname()
  const router = useRouter()
  const [showList, setShowList] = useState(false)
  const handleShowListChange = useCallback(
    (next: boolean) => {
      router.push(next ? `${pathname}?${NAV_LIST_PARAM}` : pathname, { scroll: false })
    },
    [router, pathname]
  )

  return (
    <>
      <Suspense fallback={null}>
        <NavListQuery onChange={setShowList} />
      </Suspense>
      <Navigator
        value={pathname}
        showList={showList}
        onShowListChange={handleShowListChange}
      >
        …
      </Navigator>
    </>
  )
}
```

### Section roots

A section's route shows its generated list by default. `root='page'` on
`Navigator.Secondary` shows the page alone there instead, full width at every
size — no list pane and no Back. Sub-pages behave the same in both kinds: a
list column beside the page from `lg`, the page on top with Back to the section
route when panes stack. On a phone, tapping a page-first section's tab on a
sub-page goes to its root, like iOS; on the root it scrolls the page to the top.
`showList` still shows the list over a sub-page, and is ignored on a page root.

Use a page root when the section has an overview worth reading — Home, a
dashboard. Use a list root when the section is a catalogue you pick from —
Components. A page root needs the section's `href`; without one the section
gets the routeless warning and behaves as a list root.


#### Items inside a page

`Navigator.SectionItems` renders a section's items as a grouped `List` — the
same rows as the generated list pane, with each item's `description` as
secondary text. It takes `value` (a section's item value; omit it for the
active section), `className` and `List`'s props, and renders nothing when the
section isn't found.

For anything richer, `useNavigatorSection(value?)` returns the same data for
you to lay out. It is computed during render from the navigation you declared,
so it works in the server render; with a `Navigator.Primary` that is not a
direct child of `Navigator`, it returns `null` until the Primary mounts. The
result is a fresh object each render — read its fields rather than keying an
effect on it.

```ts
type NavigatorSectionData = {
  value: string
  label: ReactNode
  href?: string
  groups: {
    title?: ReactNode
    items: {
      value: string
      label: ReactNode
      href?: string
      icon?: ReactElement
      description?: string
      badge?: ReactElement<BadgeProps>
      current: boolean
    }[]
  }[]
}
```

Loose items come back as a group with no title, in source order. `description`
is shown only by `SectionItems` and returned by the hook — never on a tile, the
bar, the list pane or More.

```tsx-live-noinline
function HomeCards() {

          <p className='text-sm text-subtle'>{item.description}</p>

    </div>
  )
}
```

### Visibility priority

Whatever doesn't fit folds into More — on a phone past five slots, the pinned
circle included, on a large screen when the window is too short. Priority decides membership, never order.

`visibilityPriority` is `'low'`, `'automatic'` or `'high'`, on an item or a
group (an item's own wins). Items rank by priority, ties by source order, and
the kept items render in source order. On a phone the bar holds five slots and
the first pinned item's trailing circle takes one of them: every item fits when
there are few enough, otherwise the top four plus More — three beside the
circle. Further pinned items fold into More.
Nothing folds while the vertical navigation is expanded — the cluster scrolls
instead. Here Orders
and Messages keep their place on the phone bar; on a large screen all eight fit
this frame, and Help would be the first to fold in a shorter one.

#### Compose the More pane yourself

### Menu

### Expanded

Phones have no expanded state, and the toggle doesn't render there.

Navigator never touches storage. Persist the choice in a cookie; if you render
on the server, read it there and pass `defaultExpanded` — the first paint is
already right, no script needed.


### Pane header

## Pane surfaces and the mobile stack

Both belong to [`Pane`](/components/pane) rather than to Navigator, so they are
documented there. The two facts worth knowing from here:

- **Below `lg` panes stack**, full-bleed, one visible at a time, and push/pop
  between them animates. Opening or closing More switches instantly. Which pane is on top is derived from the deepest pane
  marked `current` — declare it, and the arrangement follows.
- **`Navigator.Content` is the orchestrator.** Panes announce themselves to
  the nearest `Navigator.Content` through context, wherever they sit in its
  subtree — a pane returned by a route, a Next.js parallel-route slot, or a
  wrapper component all participate normally. What still breaks is having no
  `Pane` reachable at all: nothing registers, so stack position, push/pop
  motion and `primaryNav` all stay inert, and `Navigator.Content` warns to
  the console about it in development.

## Guidelines

- **Drive selection from the router.** Navigator is controlled. Derive
  `value` from the URL and give each item an `href` so back/forward and
  deep links work; reach for `onValueChange` only when there is no route
  to own the state.
- **Put pinned items last.** The vertical navigation renders its regions in
  order — brand, cluster, pinned — so a pinned item is always tabbed after the
  cluster, wherever you write it. Write it last so source order matches; one
  written before the cluster warns in development.
- **Pass bare icons to destinations.** Navigator renders an item's `icon`
  duotone at `size-6`, so pass `<TicketIcon />` without a `weight` or size
  class. `Navigator.MenuItem` icons aren't included — give them `weight='bold'`
  and `size-4` like any other icon.
- **Let the top pane declare what the mobile bar does.** `Pane`'s `primaryNav`
  is `auto` by default: the bar collapses to the active tab as the pane
  scrolls and returns at the top. `visible` pins it, `hidden` takes it away
  for the pushed screen (iOS's `hidesBottomBarWhenPushed`).
- **Panes scroll through a `ScrollArea` viewport.** `Pane` renders a
  [`ScrollArea`](/components/scroll-area) whose viewport
  (`[data-slot="pane-viewport"]`) is the real scroll container — anything
  reading `scrollTop` or calling `scrollTo` on a pane must target the
  viewport, not the `<section>`.
- **Sections without a list remember where you left them.** An item with no
  `Navigator.Secondary` that sits over sub-routes returns you to the one you
  last visited, not its `href`. That memory lives only in the running app, so a
  reload starts at the declared `href`. A section with a `Navigator.Secondary`
  always links to its section route, where its list marks the current row.

## Accessibility

- **Landmarks**: `Navigator.Primary` renders one `<nav>` per orientation. The
  vertical one carries your `aria-label`; the phone bar's appends " tabs", so
  `aria-label='Main'` gives "Main" and "Main tabs". `aria-label` on
  `Navigator.Primary` and `Navigator.Secondary` is **required**.
- **Capsules** are lists named by their group's `GroupTitle`, which stays in
  the accessibility tree while collapsed, shut to zero height.
- **Tile names** are visually hidden text inside each tile, not `aria-label`,
  so they translate with the page. The tooltip is `aria-hidden` to avoid a
  double announcement, and a badge's full label is announced after the name.
- **Current destination**: the page's own item or row carries
  `aria-current='page'`; a section's tile reads current while you are anywhere
  in the section.
- **Page roots**: on a page-first section's own route the page is the root of
  the stack, so it shows no Back; its sub-pages get Back to the section route
  like any other.
- **`Navigator.ExpandToggle`** is a button with `aria-expanded` and
  `aria-controls`, labelled "Expand sidebar" or "Collapse sidebar" in visually
  hidden text, with the same label in its tooltip in both states.
- **`Navigator.Brand`** is a link home named by its content — "Oztix" (or
  "Oztix Studio") from the default `Logo`, or your mark's `alt` or
  `aria-label`, or its text — so it needs one that reads in both states.
- **Tab order** follows the vertical navigation's regions — brand and its
  toggle, cluster, pinned.
- **Menus** are Base UI menus: arrow keys move between rows, typeahead jumps to
  one, and Escape closes the menu and returns focus to its trigger.
- **Covered panes** are hidden from assistive tech below `lg`, where panes
  stack.
